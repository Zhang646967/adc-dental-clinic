# 报告提醒、检查进度与报告办理

承接 005 常用页面。对照实际页面选择本批工作，优先级依据是从常用入口往下走的距离、读错后的影响、三个岗位能否按同一病例核对。当前没有线上点击量统计。

| 顺序 | 患者 | 前台 | 医师 | 排序依据 |
| --- | --- | --- | --- | --- |
| P0　本批 | 报告提醒 → 查结果及复诊时间 | 本店检查进度 → 患者能否查阅、是否有联系期限 | 检查工作清单 → 核对报告、选择办理事项 | 旧页面多条提醒同名；编号先于结果；新版草稿可能与患者可读版本同时存在 |
| P1　接续 | 费用清单 → 对照当前余额与历史账单 | 离店交接 → 待收、应退与待复核 | 就诊结束 → 核对实际处置与收费项目 | 就诊摘要已优化，往下一层需继续区分应付、实收和应退 |
| P2　接续 | 改期 → 保留原约、选新时段 | 按姓名或编号找患者 → 核对同名记录 | 接诊后进入结构化病历 → 找到草稿、签署及补记 | 涉及多个状态和表单，单独安排输入、大字与读屏回归 |

## 双端行为及接口

- R1 患者本人可从正常就诊入口打开提醒。每行先显示具体检查项目和发布、更新或撤回状态，再显示未读/已读、门店和时间。只给当前可查阅版本提供报告入口；撤回后保留联系门店、原就诊。主动标记已读仍是独立确认动作。浏览、展开和返回零业务写入。
- 提醒列表沿用 `GET /api/mini/v1/report-notices/` 与网页共用的本人投影。每行新增可选字符串 `project`，值取申请时保留的检查项目名。旧客户端可忽略此字段；旧后台缺字段时显示已有服务端标题。版本、读态、分页和授权沿用已有契约。
- R2 报告页默认显示项目、现行版本、发布时间、检查结果原文及可用复诊安排。已约显示预约状态、北京时间及门店。建议窗口与已约时间分开显示。患者查看已取消、已改期、未到诊或已结束的复诊时，双端把该时段标为原预约时间，回查入口指向该条历史预约。报告接口的 appointment 可选布尔字段 historical 表示这一点，旧接口按已有预约状态展示。展开、收起与查阅均不改变预约。实际检查时间、检查编号及原就诊编号可展开。报告原文、撤回影响、联系期限和主要动作不能折叠。失效链接显示原有拒绝并清除上一身份的内容。
- R3 前台默认看到检查项目、办理进度、患者可查阅状态，以及服务端已有的联系状态和期限。需要区分两条同名检查时可就地展开编号。使用现有门店范围，前台页面不得包含报告正文及医师表单。
- R4 医师清单先呈现当前患者、项目、进度与患者可见状态。详情区分最新办理版本与患者当前可查阅的版本；二者不同时，两份正文均直接可读。其他历史版本和操作日志按需展开。可执行项目有具名入口，表单出错时重新打开原项并显示原输入与错误；发布或撤回、独立审核、再核对后确认均走原流程。
- R5 按现有字体、原生可展开控件和相对字号实现。目标触区至少 44 个逻辑像素。浏览器以 375、390、430、1280 宽及常规、200% 字号检查换行、焦点、表单、返回与正文。手机另验紧凑/标准/大屏、系统与微信大字、iOS VoiceOver、Android TalkBack，逐项记录实测条件。

## 交付与验收

Codex 负责网页、共用投影、本地 PostgreSQL、角色及浏览器回归；WorkBuddy 在同一候选上改患者端提醒清单和报告详情。使用独立合成样本，对齐已更新、撤回、待发布、联系、已约、有建议尚未约、代约和其他患者。医师表单可在独立库核对错误或进入预览；本轮展示验收保留原预约、版本、联系与资金事实。

网页、官方开发者工具、关闭调试的实机三类证据分别记录。实机记录实际逻辑宽、机型、系统、微信、字号、读屏与动作，缺设备的单元标待条件。双端与实机完成后再决定更新老师入口。
