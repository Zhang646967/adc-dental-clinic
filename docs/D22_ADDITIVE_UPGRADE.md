# D2.2：追加迁移升级与失败处置

核对旧版和目标 → 暂停写入 → 加密检查点 → 追加迁移 → 验证后恢复服务。

适用于统一 ADC 的直接 HTTPS 部署。保留原数据库、账号、绑定、配置和数据卷。实例先使用包含本批升级入口的部署控制器；早于本批的远程入口可能无法识别新参数，不能把当前控制器的能力归给旧部署脚本。当前没有实际云端实例。

## 办理方式

部署维护者核对目标镜像和源码清单，审查新增迁移的内容与 CI 结果。自动核对包括旧迁移原字节、实际已应用迁移名、目标依赖图、事务化正向计划和主机／数据库磁盘余量。正向计划检查不能代替审查新增 SQL 或数据迁移的语义。

在既有 `g4_course.py upgrade` 或 `g4_remote.py upgrade` 参数后加 `--allow-additive-migrations`。仍须指定 `--artifacts`、`--recipient-file` 和 `--expected-current-commit`；期望提交为**升级前**的完整应用 SHA。未加该选项时，升级继续只接受相同迁移集。备份使用部署已有的加密接收方。

同一部署只允许一个发布操作。先停网关及业务／通知写入，保留独立加密检查点，再由既有数据库 owner 按 Django 正常迁移顺序运行。应用迁移集合准确一致，角色、通知／观察和 HTTPS 检查通过后才恢复服务。原迁移、已有业务记录及密码不由发布工具改写，初始化也不会重跑。

## 失败后怎么做

| 私有发布记录 | 维护动作 |
| --- | --- |
| 备份前后出错，尚未启动迁移 | 尝试恢复原镜像；核对原站状态和私有日志后重试。 |
| 已开始迁移、进程中断或候选运行检查失败 | 保留网关关闭、原数据库和检查点。检查失败原因及实际迁移；确保原迁移容器已退出，使用原命令、原期望提交和同一个目标包继续。 |
| 已应用全部迁移，但发布应答丢失 | 原命令继续核对并完成恢复；已通过的目标重复执行返回已启用。 |
| 需要检查升级前的数据 | 将加密备份恢复到另一个空库，使用匹配的旧镜像和迁移建库模式。 |

状态保存在 `private/release-operation.json`；日志和备份只保存在私有部署位置。若命令中断后仍有该项目的 `_release_schema` 容器，先核对其是否在运行，不能并行启动第二个迁移。迁移已经开始后不会自动切回旧版，不逆向迁移，也不把备份写回运行库。已经过验证的相同结构镜像回退路径保持原样。

本批不增加业务数据库结构；验收样例使用既有三份追加迁移（77→80）。云端 SSH、目标机容量和独立运行另验；不要求小程序重新部署。

思维导图：确定版本 → {原迁移、实际历史、备份} → 维护 → {追加、继续、核对} → 恢复服务；独立空库用于恢复验证。

[本批实测与准确CI](evidence_d22/README.md)。若处置必须更改目标代码或迁移，先核对已应用的迁移和原检查点，按单独审查方案修复；不能拿不同目标包冒充原操作继续。
