# C0.4 患者找店与登录分流合同

访客浏览 → 主动定位或选城市 → 门店营业与服务 → 患者登录 → 就诊人 → 原预约确认。

当前为源码候选，承接[下一阶段计划](PATIENT_DISCOVERY_AND_INSURANCE_PLAN.md)。验证、准确提交CI、报告、独立恢复及本机安装分别记载，不能以本合同替代执行证据。

## 门店资料与营业来源

主管仅维护当前诊所的对外名称、行政区、地址入口、公开电话、坐标来源和发布状态。新增门店公开资料及追加版本两张表，保留原Clinic主键、业务编码、名称和历史单据。资料经签名预览与明确确认保存；同一操作重试返回原结果，旧版本不能覆盖新版本。版本记录由PostgreSQL拒绝普通更新和删除，存在新资料时拒绝破坏性逆迁移。

营业时间直接投影现有有效科室的DepartmentHours和科室停用区间。任一科室开放时可显示门店营业；全部科室暂停时显示休息。科室、诊室和设备的新增预约核验继续由原资源模块负责。“有公开出诊日期”不是“有兼容资源或患者可用余位”。内部停用原因不公开，主管仅可另填对外说明。

公开资料确认与原资源维护共用物理资源锁，递增资源目录版本，因此更名前的预约预览不能直接确认，撤回再发布也不复活旧预览。已确认预约和有效邀约不因公开资料更新而取消或释放；新资源方案保留当时门店公开名称和联系信息快照，旧记录不补造新快照。实际搬迁仍须由前台核对原承诺及到诊安排。

## 访客与定位

网站首页和门店页、原生小程序访客首页均公开浏览。匿名接口只提供已发布的门店、服务和出诊参考，不创建工作上下文、患者、预约、治疗或资金记录。尚未准备新资料的历史公开服务沿原范围可读；显式撤回门店资料后，其公开新服务入口一并隐藏，原预约仍按原权限可读。

定位仅由用户主动触发。两端距离计算使用WGS-84，地图导航使用另行核对的GCJ-02点；坐标缺失不作为零坐标。坐标在客户端排序，不提交或保存患者定位轨迹。距离为直线估算，未知距离排后，相同距离按稳定门店编号排序。用户可以拒绝定位、手动选城市及搜索区域。

合成门店明确标识环境，拦截真实拨号和地图跳转。真实门店的拨号和导航为显式操作，号码和坐标由主管核对后发布；没有导航坐标则不提供导航操作。地图网页使用高德[官方URI标注接口](https://developer.amap.com/api/uri-api/gettingstarted)，原生端使用微信地图接口。外部地图及真机权限仍需实际环境验收。

## 登录通道与预约延续

登录通道保存在服务器WorkspaceContext中。患者网站及小程序仅激活PATIENT；员工网站仅激活有效非患者岗位。多岗位员工仍可在员工通道选择其授权岗位。通道不授予新角色、诊所、PatientAccess或代约授权，换一个页面或提交隐藏角色字段不能越过通道。

追加迁移按既有角色将旧HTTP上下文归入患者或员工通道，保留原角色、诊所及版本。可信内部命令或测试可保留无通道上下文；HTTP创建和登录均明确通道，客户端不能提交该字段。数据库约束也拒绝患者岗位与员工通道的矛盾组合。

访客选择服务后才登录。网站将服务选择绑定账号与服务器上下文，原生端仅保留短期、数值型门店和服务提示；这些提示均不是预约权限。需要选择授权患者时保留原服务，选择后重新核对当前服务、诊所、患者授权和资源。换账号、过期、下架或撤权不创建预约，也不替换成另一项服务。

## 数据与交付

原49份迁移保留，新增registry、scheduling和workspaces各一份追加迁移。公开资料版本、停用对外说明和登录通道需要真实数据库关系核对；当前正式ER及报告仅在实际迁移、取证后更新。课程八城二十店配置通过现有登记、授权、资源及排班命令办理，不用直接SQL重写旧门店，不生成临床或资金事实。

C0.4验收对应DISC-01至06及登录分流，覆盖匿名浏览、拒绝定位、双坐标、营业例外、版本与并发、服务登录延续、跨店权限、历史预约和资金保持，以及390px大字与键盘。微信身份及医保阶段仍按C1-WX、C6.1和C6.2分别推进。

思维导图：公开资料及版本 → {名称位置、营业来源、服务发布} → 访客找店 → {定位、手动城市} → 分流登录 → 明确就诊人 → 原预约规则 → 历史和资金保持。
