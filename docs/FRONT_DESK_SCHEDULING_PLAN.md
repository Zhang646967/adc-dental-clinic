# B1.3.1 前台排班与数据库设计优化

前台排班责任 → 可办理的日周排班 → 明确的数据关系 → 资源与患者协调 → 场景验收。

用户已明确：排班由前台负责。下一阶段先完成这项岗位调整和数据库设计优化，再进入B1.4患者自助改期。2026-10-20本次交付是规划、当前数据库ER及报告更新；下列应用功能尚未实施，不能引用B1.2＋B1.3的历史通过作为本阶段验收。

## 已核对的起点

- 已有电话接待、统一服务和物理资源占用、前台代约改期、故障影响及兼容替换。
- 当前`create_slot`、出诊调整／停用、暂停／恢复接收，以及候补建议生成／发布仍要求MANAGER。菜单与服务端权限均需调整，增加一个入口不能完成岗位迁移。
- 原报告有领域类图和状态图；旧`PHYSICAL_DESIGN.md`、`FIELD_CATALOG.md`是v0.3历史材料，不能作为当前数据库设计。已新增[当前数据库ER与字段目录](database/README.md)：69张表、170条实际SQL外键，包含真实连接表、可空及唯一关系。
- 现有31份原迁移、既有历史与RC标签继续保留。此次只读结构核对未查询业务行；未改动运行权限、业务数据或数据库结构。

## 岗位合同

| 工作 | 日常负责人 | 协作与边界 |
|---|---|---|
| 查看日／周安排，按店和医师定位余量 | 前台 | 汇合出诊、预约、邀约及椅位设备事实；查询不占位。 |
| 登记出诊、调整未来空闲出诊、停诊与恢复接收 | 前台 | 依据诊所确认的医师工作安排；不得覆盖已有预约或有效邀约。正常操作无需让主管逐条代办。 |
| 候补建议、逐项核对及限时邀约发布 | 前台 | 保留人工确认；不代患者自动接受，不改变既有预约。 |
| 已有患者承诺的调班协调、联系和结果登记 | 前台 | 先保留原约，明确责任与期限；改变时间或医师须取得同意，失败保留原结果。 |
| 科室、诊室、服务时长、必要设备及资产目录 | 主管 | 管理供给规则，前台按已生效规则排班；目录变更不重写历史。 |
| 例外协调结果、维修恢复等现有独立复核 | 另一获授权主管 | 复核依据及结果；不变成所有日常排班的新增审批。财务和医疗权限保持原有分工。 |

前台操作仅限当前店；一名医师跨店出诊仍不得重叠。医生仅取得自己的授权范围，患者只取得本人可预约安排，总部查看汇总。前台承担排班不扩大其临床、资产验收或财务审核权。

## 实施顺序

| 批次 | 具体业务交付 | 完成门槛 |
|---|---|---|
| 设计基线（本次） | 当前ER、字段与外键目录；排班职责和需求至验收追踪；报告统一入口 | 图、表、真实结构相符；当前权限与待调整职责分别说明。 |
| 第一批：前台排班 | SU-19、29、30、32、33及候补SU-14、15转到前台当前店工作区；菜单、签名、服务授权、撤权及通知目标一并调整 | 前台独立完成一次出诊登记、调整、暂停、恢复和候补发布；旧主管页面及旧确认安全失效；保持独立复核。 |
| 第二批：日周操作 | 按日期／医师查看排班与占用；显示诊室椅位和必要设备余量、停用及维修原因，提供明确办理入口 | 电话受理可从同一工作流核对可行时间；无空档、停诊、邀约和实际在诊均有正确解释；键盘及390px大字可用。 |
| 第三批：数据关系优化 | 以ER逐项评审归属、主外键、可空、唯一、状态及时间约束；有实证再调整表、约束或索引 | 每个变更有业务问题、数据字典差异、迁移与反例测试；不为图好看拆表、复制占用或引入第二份排班事实。 |
| 第四批：完整验收 | 前台排班→电话／网站预约→调班协调→到诊→治疗结算，含跨店及并发 | 原约和资金不被排班改写，真实数据库并发及七角色通过，报告与实际版本一致。 |

第一批先复用`AvailabilitySlot`及既有变更历史；批量周模板、请假／停诊申请是否需要独立实体，在明确重复操作与追踪问题后再设计。不得先复制一套“排班表”并与预约库存各自维护。

## ER与数据库评审重点

| 优先项 | 需要回答的具体问题 | 设计与验收产物 |
|---|---|---|
| 排班事实与占用粒度 | 医师出诊、科室开放、服务时长、椅位／设备暂占和正式占用分别是什么事实？ | 字段、区间边界、唯一性和释放条件；两个入口争抢同一资源仅一个成功。 |
| 诊所归属 | 不同对象通过哪条外键路径归属于诊所？重复clinic引用何时必须相等？ | 关系路径清单；逐项区分DB约束、命令重检及尚缺护栏；跨店反例。 |
| 版本与当前记录 | 方案、凭据和治疗版本如何保留过去并指向当前？ | 条件唯一、版本链和追加历史说明；纠正不重写历史；不把条件唯一标成永久一对一。 |
| 空值与状态 | 咨询未建档、未成约、未匹配和已释放分别允许哪些空值？ | 状态—必填关系矩阵、异常处理和约束覆盖；不补造历史关系。 |
| 金额与诊疗 | 一个就诊、一张逻辑账单、多次收退款、凭据版本和对账如何衔接？ | 保留账单同次就诊复合外键；按实际治疗和已记账资金独立核算。 |
| 查询与性能 | 日周排班是否出现逐行查库、遗漏邀约或历史联接重复计数？ | 代表性查询与执行计划、索引依据；分页后仍有完整冲突判断。 |
| 已发现的类型差异 | `auth_group_permissions.id`模型声明integer，实际为bigint，来源是否为框架历史迁移？ | 目录先按真实类型记录；追踪迁移和模型声明，不直接缩窄已有主键。 |

图和数据字典是评审入口，不代表全部跨表规则已由数据库独立强制。此次确认170条外键存在，未把这项结构核对表述为全库数据完整性或下一阶段容量验收。

| 编号 | 可观察行为 | 验收场景 |

| DATA-01 | ER准确表达真实主外键、可空、连接表和条件唯一 | 重新提取结构并比对；每条图边可定位真实外键，SQL-only复合外键单列。 |
| DATA-02 | 新数据规则不破坏原临床、资金和历史 | 同版本独立恢复、迁移前后行核对、预约→治疗→结算独立核算。 |

应用修改后执行完整回归、真实PostgreSQL授权与并发、浏览器及必要恢复。容量结果按实际执行版本另存；本次文档更新不重贴旧容量为新结果。功能通过后才更新本机应用，并同步准确版本及报告。

思维导图：前台排班 → {出诊与候补、日周视图、调班联系}；数据库设计 → {实体、主外键、可空、唯一、状态与历史} → {资源争用、患者承诺、诊疗资金} → 可执行场景与报告一致。
