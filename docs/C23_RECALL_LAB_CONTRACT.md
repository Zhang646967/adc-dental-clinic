# C2.3 复诊责任与加工件就绪

医师明确目标 → 前台接续责任 → 实际联系与资源成约 → 加工送返及临床验收 → 核对实际完成依据。

## 复诊责任

医师后续要求保留服务、具体步骤、建议日期及完成标准。前台明确承接责任和内部跟进期限，记录实际联系、未取得回复或内部协调。本人暂不继续转入医师核对；没有明确恢复依据不继续对外联系。原责任人失效时，另一位当前店前台可以明确接续，历史不删除。

关联预约、接通电话、返回加工件均不构成复诊完成。完成必须选择明确关联的后续预约及其唯一改期链上、同患者同店同服务且已关闭的实际就诊。检查目标引用确认检查，步骤目标引用指定版本已完成的实际执行；部分治疗不提前关闭目标。晚于原窗口照实保留迟延，不改原建议日期。医师撤回原要求后，前台可明确结束责任；取消预约并不撤回医师要求。

思维导图：后续目标 → {责任人、期限、联系结果} → {安排、医师核对、恢复、撤回} → 实际完成依据。

## 加工件就绪

医师针对已接受的具体方案步骤明确加工依赖，并从本次确认检查登记加工要求。前台认领、手工登记送出、返回、延迟及交接凭据；这些是操作者登记的事实，不是外部供应方回执。原需要日期、临床要求及既有预约保留。前台只能看到安排投影，不读取加工临床规格或医师验收详情。

返回后由具备具体服务记录范围的医师验收。返工必须有前台协调说明并经过下一次送返周期；新版方案沿用加工件时必须明确验收具体新版步骤，不能仅凭稳定步骤沿革自动复用。全部有效加工请求在当前周期及确切版本通过后，相应实际执行才可确认；缺失历史依赖保持未明确，不推断为无需加工。实际执行时间不得早于适用的验收时间。行政责任交接不使未改变的临床验收失效。

加工状态为待安排、已送出、已返回、已验收、需返工、明确撤回。加工请求和验收不会自动产生治疗、收费、退款、预约或改期。临床实际执行继续由原唯一收费桥接处理。

思维导图：已接受步骤 → 明确依赖 → 手工送返 → {适配验收、返工新周期} → 具体版本就绪 → 原实际执行命令。

## 数据与模块关系

追加五张表：随访责任及事件、加工请求、验收及事件。方案步骤增加可空加工依赖和发布时目录定义；历史空值不补造。后续要求增加完成标准，历史为未明确。确认版本、患者决定、实际执行、原收费快照和加工／随访历史均保留。

同版本 PostgreSQL 验证库实际观察为101张表、100张ORM表、966个ORM列、282条SQL外键和74个应用触发器，执行49份应用迁移；原47份迁移逐字节保留。六幅新增ER与完整字段目录均从实际结构生成。数据库触发器保留跨表完成依据、加工验收及追加历史规则；命令继续锁定当前主体、授权、患者和对应业务记录。
