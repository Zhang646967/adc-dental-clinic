6. 配置你自己的 AI：不要发密钥到聊天

原目录 CMD 运行以下临时容器命令，不依赖损坏的 Windows Python：

docker run --rm -it -v "%cd%:/app" -w /app python:3.13-slim python scripts/configure_ai.py

根据提示输入 remote、服务商文档中的 HTTPS Base URL、可用模型 ID、支持的 token 字段，并在隐藏输入处粘贴 Key。Base URL 不应带 /chat/completions 尾缀。脚本只更改 AI_* 行，保留原数据库连接和 Django 密钥，不发送网络请求。

适配器要求 POST /chat/completions、messages、JSON object 输出和相应 token 参数。它不是所有服务商原生 API 的通用适配器；兼容性须通过服务商文档与实际测试确认。本版不实现仅 Responses、Gemini 或 Anthropic 原生协议的转换。

然后执行：

docker compose up -d --force-recreate web
docker compose run --rm web python manage.py check_ai

第二条只显示模式、是否配置Key和模型，不回显任何密钥，不发网络请求。

明确接受一次服务商可能计费的合成测试后，才执行：

docker compose run --rm web python manage.py check_ai --live

该测试只发送“我想预约”和固定分类提示，不发送数据库记录。真实聊天还需要在页面勾选问题文本外发同意。Key 错误、模型不兼容或网络故障会清楚标记为本地降级，不悄悄伪装成功。

切回本地演示可再运行配置脚本并输入 demo，重建运行中的 Web 容器即可。禁用模式不会自动删除环境中的旧密钥；如需撤销密钥应在服务商侧执行。

双端 AI 接口与信任边界 v0.4

性质：[D] 本项目工程设计；不是病例诊断或医疗效果评估。

1. 为什么不把患者数据库交给聊天模型

本版把语言模型用作受限意图分类器，而不是自由生成答案的业务操作者。模型可能误分类；权限和数据更新的合法性不能依赖模型判断。受控卡片回答减少未经来源支持的内容，但不意味着语言理解绝不会出错。

浏览器（session + CSRF；无Key）
 → Django：身份/角色/患者绑定、输入与限额检查
 → 医学问题本地转人工；未同意不外发
 → ProviderAdapter（HTTPS、主机白名单、密钥仅服务端）
 → 模型输出 intent + confidence
 → 严格字段校验，超范围/低分/非法响应回退
 → 再次核对当前授权，从本系统查询事实
 → 固定文字、事实、来源、时间、业务入口卡片

业务提交仍走普通表单 → 用户显式确认 → Django 服务 → 数据库约束及事务。助手代码没有调用创建、取消、治疗或结算服务。

2. 内部接口

POST /api/assistant/patient/ 与 POST /api/assistant/staff/，要求已登录、session cookie、CSRF token 和 Content-Type: application/json。

{"message":"查看我的预约","consent":false}

严格只接收 message（1–800字）和 consent（布尔），不接收患者编号、任意SQL、角色、URL、模型、Key、账单金额或工具名。原始请求体上限8192字节。

成功返回的模式示例（说明字段，非实际API测试记录）：

{
  "request_id":"由服务器生成UUID",
  "mode":"demo",
  "mode_label":"本地规则演示（未调用AI）",
  "intent":"appointments",
  "title":"你的预约概览",
  "answer":"规则说明",
  "facts":["当前账号的有限预约摘要"],
  "links":[{"label":"查看我的预约","url":"/portal/appointments/"}],
  "source":"PORTAL-02 · 本人数据范围",
  "as_of":"查询时刻的ISO时间",
  "actions_executed":false,
  "notice":"本次对话没有修改业务记录。"
}

400格式问题，401未登录，403授权/CSRF问题，413过大，415格式类型错误，429限额，503内部暂不可用。后端不把模型错误正文、认证头或堆栈放进响应。业务页面仍可用。

患者意图：预约入口、本人未来预约、取消步骤、账单说明、显示偏好、人工帮助、医学转人工、通用帮助。 员工意图：授权范围内今日计数、预约规则、接诊步骤、开单规则、显示偏好、医学转人工、帮助。

本版不抽取“下周三”等相对日期；摘要明确使用服务器定义的范围。提示用户到普通时段表单选择日期，不能假装模型已经精确查询自然语言指定的日期。

3. 外部接口契约

assistants/provider.py 使用Python标准库发送 HTTPS base_url + /chat/completions。不引入浏览器SDK、不向客户端返回密钥。

请求包括固定 system 分类提示、经过有限遮蔽的单条问题、服务商模型ID、response_format={type:json_object}、256的输出token限制以及stream=false。max_completion_tokens或max_tokens可配置。不自动重试；超时默认20秒，响应最多32768字节，不接受重定向，不接受工具调用或非stop结束结果。

模型仅可输出：

{"intent":"book","confidence":0.92}

不允许多余字段、任意链接、SQL或解释文本。confidence低于0.65进入通用帮助；这个分数不是已校准概率，阈值是待真实数据验证的工程启发式，不在界面伪装成诊疗准确率。

配置键

配置 默认/含义
AI_MODE demo / remote / disabled；默认demo
AI_API_KEY 空；可兼容读取OPENAI_API_KEY作为后备
AI_BASE_URL https://api.openai.com/v1；可换可信的兼容服务

限额记录存PostgreSQL以便多进程共享；所有助手请求都受计数，拒绝超过限额的请求。请求次数上限不是人民币/美元消费预算。服务商侧仍应设置单独限额、监控和密钥权限。

check_ai 不发送请求；check_ai --live 是运维主动发起的单次合成检查，可能计费，独立于用户请求配额，不应开放为公众接口。

4. 数据最小化

服务端不会附带患者姓名、病历、完整预约、过敏或账单记录给模型。用户主动输入的问题文本仍可能含个人信息：邮箱、常见电话和长数字做有限遮蔽，不能承诺去除姓名、拼音、地址或所有敏感内容。外发前须同意；项目仅使用虚构数据。第三方保留/训练/地域条款由所选提供商决定，本代码不保证“零保留”。

原始对话不写数据库或技术日志；只写账号ID、请求ID、角色入口、类别、模式、错误码、字符数和耗时。浏览器只在当前DOM中显示对话；localStorage仅记显示偏好。关闭或刷新页面清除对话，不是跨设备聊天历史。助手元数据有技术追溯作用，不构成病历。

可选朗读使用浏览器报告为 localService=true 的中文声音；没有则禁用朗读，不改为云TTS。没有麦克风录音、文件上传或语音识别。浏览器/系统语音实现仍应在目标设备验收。

5. 故障与攻击面

风险 已编写措施 残余边界

正常路径

  1. 使用独立浏览器会话，以patient_demo_a登录 /portal/login/。确认显示自己的虚构名字，没有其他患者的档案列表。
  2. 切换大字简明模式，再切回；用Tab访问主要按钮。手机用开发者工具模拟390px与320px，检查布局而非仅截图美观。
  3. 进入预约时段，选择甲店的牙医1。确认页核对诊所、牙医、北京时间；勾选确认后提交。刷新或重复成功提交不产生第二条。
  4. 用front_a打开新预约，确认患者身份后登记到诊。演示允许前台登记到诊，其真实机构提前到诊政策尚未另行制定；不把未来计划时间改成当前时间来抹历史。
  5. 用doctor_a打开接诊工作台，复核过敏状态，不能把未知当无已知过敏。添加已经实际提供这一含义下的虚构治疗，检查目录价格和单位。

  7. 用patient_demo_a查看自己的账单；以patient_demo_b访问同一URL必须被拒绝。账单为开单金额，不代表支付成功。
  8. 另建无治疗演示预约，登记到诊后选择无治疗关闭、填原因，不添加治疗。应有到诊事实、零明细、零金额单，不能出现虚构收费行。

课程报告增量章节：双端服务与受限AI v0.4

1. 来源与需求变更

ADC案例的信息需求以患者、多过敏、跨店牙医、实际治疗、季度业绩和一就诊一结算单为主（CASE第1–2页）。它没有要求患者网站、生成式AI、具体无障碍尺寸或技术栈。本轮新增这些内容，依据用户在本次开发会话的明确扩展要求 [U]，实现规则为项目设计 [D]，不伪称真实诊所访谈已确认。

NOTE3第1页要求需求可追踪至设计与代码，第11页给出模型不变量及操作前后条件；NOTE4第7页强调功能和数据并行细化、第11页强调模块联系明确。本轮据此新增PatientAccess、BookingReceipt、UsageBucket和AssistantEvent，并保持原Visit和账单不变量。

2. 架构与业务控制

患者端与员工端共享Django/PostgreSQL，但使用不同身份/角色边界。患者自助预约必须通过已绑定账号、10分钟签名确认页面、再次资源检查和数据库排斥约束；聊天只负责解释与导航，不能绕过这些要求。

接诊服务由负责牙医执行：复核过敏资料的当前版本、记录实际治疗及目录快照、核对完整费用、在同一事务内发布记录并生成唯一结算单、更新就诊结果和审计。未知过敏和无治疗不是同一个概念；无治疗关闭不伪造治疗，保持到诊事实并产生零明细零金额结算单。

3. AI交互设计

大模型被限制为意图分类器，仅返回受控类别及一个待校准的分数。服务端严格校验后重新核对权限，采用固定业务说明和查询结果构造答复卡片，显示规则来源和查询时间。员工得到其权限范围内今日计数和流程指导，患者得到本人未来预约摘要和服务入口。

这条路线牺牲了开放式对话自由度，换取更容易测试的事实来源、权限边界与故障降级。它不是完整RAG或可自主执行的Agent，也不称为在线牙医。不能仅靠系统提示词保证可靠性；工具和数据库写权限在架构上不交给模型。

默认规则演示没有外部调用；外部模式必须在服务端配置Key和模型，并由用户同意问题文本外发。第三方接口不接收自动附带的病历，但用户主动输入仍可能包含个人信息，有限遮蔽不等于完整匿名化。只存必要调用元数据，不存对话正文。

4. 包容性设计

显示偏好由使用者自行选择，而不是通过年龄预测。标准与大字模式具有相同业务能力；后者增加根字号与按钮面积，降低列数。保留非聊天入口、确认页、可聚焦控件和文本反馈。可选朗读仅请求设备提供的本地中文声音，没有则明确保持文本。未进行目标人群用户实验，不能在报告中声称已经证明对老年用户更有效。

5. 验证证据

原v0.3的30项PostgreSQL集成/并发测试已由用户提供的终端输出证实通过，随后用户截图显示本地前台已成功登录。该证据只覆盖原版本和当时场景。

本轮实际执行101项纯规则/静态/接口契约检查，以及87项Chromium静态页面/JavaScript断言。浏览器使用源模板转换和固定数据，fetch与storage为测试替身；这些不是Django模板引擎、数据库或真实模型接口的端到端结果。

本轮新增54项业务集成测试及2项并发测试；与原30项一起形成86项待Docker回归的方法。生成环境没有Django/PostgreSQL，依赖下载失败，不能声称已运行。外部AI无密钥未调用，分类准确率、成本和网络稳定性也未测。

6. 当前限制

历史更正、季度成本及绩效页面、真实身份核验、家属授权、支付退款、生产日志与完整安全审计、公网部署、备份恢复实测仍在后续工作范围。该演示不得输入真实医疗资料，不应作为真实诊疗或财务运营系统直接上线。
