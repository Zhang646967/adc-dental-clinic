# SU-26 更正患者联络资料

版本：CONTACT-09A3.1；父需求基线：R4.4；实现候选：v0.9.0-alpha.3。
本增量是对项目“最小运营维护”的具体化，不声称由课程PPT逐项规定这五个字段或15分钟期限。

## A. 业务问题与涉众

当前档案已经能够建档和查阅，但电话、邮箱或地址发生变化后，前台缺少受控更正入口。患者希望后续联系准确；前台希望一次核对后保存；负责牙医不希望临床内容被联络维护改变；财务希望历史单据仍能反映当时结算依据；维护人员希望差异、责任与重复请求有明确规则。

执行者：当前激活前台身份并选择授权诊所的工作人员。患者为资料涉众，本用例不开放患者自行编辑。
触发：前台取得患者说明，需要更新联络资料或更正已核对的录入错误。

## B. 前置、后置与业务规则

前置：账号已登录，前台工作上下文存在。对象关联、权限是否仍有效、输入是否合法属于执行中检查，不预设成功。仅使用合成演示资料。
成功后置：恰好更新经预览确认的联络字段，并保存一条与操作编号关联的审计事件。
最低保证：校验失败不写入任何联络字段；审计或保存失败时本事务不部分生效；只更正指定档案，不触碰身份、过敏、账号关联、预约、治疗及已发布账单。

|字段|长度上限|要求|
|---|---:|---|
|phone|32|必填文本，保留前导零及合理国际电话表示|
|email|254|可留空或清空，服务端复用EmailField验证|
|billing_address|255|必填单行文本|
|emergency_name|80|必填单行文本|
|emergency_phone|32|必填文本|

BR-16（本增量）：联络字段严格白名单；患者在当前店创建或有当前店就诊关系才可维护，全局精确查号本身不授予修改权。跨店患者仍是一份共享档案，修改不会复制成另一个人。
BR-17（本增量）：预览不改业务数据；最终确认必须重新校验授权、上下文和快照；同次成功请求不重复写入。
BR-18（本增量）：联络变更事件不保存原始电话、地址或邮箱。已发布结算头快照保持不变。
设计决定：预览令牌有效15分钟；更正依据从三个固定理由中选择，不允许在自由原因栏填写病史或其他敏感内容。

## C. 基本路径

1. 前台指定患者，请求更正联络资料。
2. 系统核对有效账号、前台身份、当前诊所和患者关联，提供允许维护的当前值及受签名保护的资料快照。
3. 前台提供五项完整联络字段和更正依据，请求核对变更。
4. 系统复核权限与资料版本，校验字段，反馈变更前后的差异；此时不写入业务数据。
5. 前台核对患者、差异与业务边界，明确确认保存。
6. 系统在同一事务中锁定授权上下文及目标患者，校验签名、时间、对象、资料指纹和操作编号，更新允许字段并记录事件。
7. 系统反馈本次保存结果并返回同一患者的档案；前台核对当前值。

### 扩展路径

- 2a／4a／6a 无关联、停用或无权限：拒绝，不暴露越权患者；账号拥有其他身份不抵销当前身份限制。
- 4b 输入缺失、超长、非法邮箱、不可见控制字符或夹带姓名/过敏字段：指出原因，不保存。
- 4c 没有实际差异：说明无需保存，不增加审计。
- 4d 编辑期间已被更新：重新读取，不合并或覆盖他人值。
- 5a 放弃：返回档案；预览不产生待办记录或部分保存。
- 6b 未明确确认、令牌篡改、过期或工作台变化：拒绝旧确认，要求查询当前资料。
- 6c 相同成功操作再次提交且仍有权限和有效令牌：返回原事件结果；后来的合法新值不被撤销。
- 6d 两个不同预览竞争：在应用行锁协议下只允许一个基于旧快照的更正；另一个必须刷新。
- 6e 联系方式A→B→A：审计游标变化，原A快照仍然过期。
- 6f 保存/审计异常：回滚；网络回执未知时先查当前档案，不把未知结果说成未保存，也不自动重放。
- 只读实例：可在授权范围读取现值，但预览写流程及最终保存被拒绝；普通查询不扩权。

## D. 分析与设计责任

|边界／控制／实体责任|代码映射|不得混入|
|---|---|---|
|前台联络资料接口：接收完整输入、差异呈现和显式确认|contact_forms.py、contact_views.py、templates/patients/contact_*|模板授权、原始SQL、模型自动决定患者|
|更正联络资料控制：编排对象、上下文、签名、事务和审计|contact_services.py|五字段以外更新、后台批量改写|
|患者实体及审计事实：保存受控当前值和最小事件|既有Patient、AuditEvent|历史Invoice版本覆盖|
|纯规则：输入限制、差异、快照与载荷格式|contact_rules.py|Django、网络、数据库、页面位置|

公开接口：`contact_editor` → `prepare_contact_change` → `confirm_contact_change`。前两个读取/验证不改变患者业务事实；最后一个为业务写命令。HTTP POST与业务写入不是完全等价，但只读实例有明确流程限制。

锁协议：最终确认在atomic事务内调用原有`lock_clinic_grant`，继而锁Patient；其他受控联络编辑需复用本命令。未新增数据库触发器，不能声称阻止DB所有者任意SQL绕过。最终授权验证、事务及行锁行为仍须在真实PostgreSQL中确认。

快照：`hash(合同版本, 患者编号, 最新联络审计ID, 五字段值)`，不是将所有其他临床资料混入版本。确认载荷绑定操作者、患者、当前诊所、上下文UUID、修订号、资料快照及操作UUID。

签名防篡改，不是加密。预览载荷包含用户已经在本页核对的联络值，只通过POST返回；禁止放入URL、日志、AI提示词。敏感POST和变量设置用于生产错误报告过滤，不代表开发DEBUG页面适合处理真实个人信息。本系统仍只允许合成数据。

## 模块总结

联络更正 → 有限字段 → 授权对象 → 预览差异 → 再验证 → 原子保存与最小审计 → 核对当前结果。
核心界限：资料维护不等于身份认领；当前地址不等于历史账单地址；预览不等于保存；签名不等于授权；测试条数不等于已验证覆盖。
