# 患者服务中心与门诊协作

## 门诊业务设计

湘雅三 e 院的电脑微信实测观察了就诊卡、挂号与候补、候诊查询、费用查询及个人中心。挂号按日期或按医师查看，退回科室检索保留关键词。首页以四个高频操作为主，门诊、住院、体检和上门服务分别分组。费用页在就诊人下区分待缴和已缴。院方也将停换诊、加号、呼叫及缴费作为门诊协作流程培训。 [湘雅三医院门诊部培训](https://www.xy3yy.com/news/zhxw/185877.html)

ADC 以门店门诊为当前服务范围，使用一次就诊关联身份、预约、临床记录和财务事实。患者网站、小程序及员工工作台各有自己的入口，复用服务端权限和业务命令。

| 责任 | 业务事实 | 患者可见结果 |
|---|---|---|
| 患者与前台 | 核验本人档案、代约或医疗代理及适用门店 | 当前就诊人和可办事项 |
| 前台与排班 | 科室、服务、医师、诊室、设备、号源、候补和到诊 | 可约时段、邀约、预约及到诊结果 |
| 医师与执行岗位 | 接诊、方案、同意、实际治疗、处方和发药 | 授权范围内已发布的诊疗信息 |
| 财务与审核 | 已发布账单、记账、退款、预收及分配 | 本人结算单、尚需支付与应退余额 |
| 门店运营 | 服务目录、出诊、设备、耗材和业务协调 | 公开门店资料与办理指引 |

## 第一批交付

- 登录后的网页首页依次呈现当前就诊人、下一步和常用办理。已登记到诊显示「已到诊」，超期预约由门店核实，候补邀约仍明确截止时间。
- 查号按日期排序或按医师分组。切换方式和返回核对页带回服务、门店、日期及医师。候选来自同一个资源查询。没有已发布出诊、没有符合条件的组合和查询失败各有说明。
- 「费用查询」列出本人的已发布结算单，沿用已记账现金、医保及预收抵扣的余额算法。开单金额、尚需支付和应退余额分项显示。原预收与资金流水从费用页进入。
- 小程序首页将就诊人、主行动、快捷办理和找店选医分层。原生改动由 WorkBuddy 在独立分支完成，按下列接口联调。正常扫码体验由已具备体验权限和合法请求域名的真机环境验收。

## 双端读取合同

| 读取 | 本轮行为 |
|---|---|
| `GET /api/mini/v1/session/` | 使用既有账号、就诊人、授权游标及 `read_only`。先显示读取中，再按返回的登录、建档、选择及办理状态渲染。 |
| `GET /api/mini/v1/overview/` | 保留主行动种类和原字段，新增 `primary_action.label`、`button`、`hint` 及顶层 `can_view_funds`。`CHECKED_IN` 的显示文案是「已到诊」。 |
| `GET /api/mini/v1/candidates/` | `clinic`、`service` 必填，`day`、`dentist` 可选。省略日期查未来十四天，最多返回 80 个候选。使用 `dentist_id` 分组，状态为 `AVAILABLE`、`NO_SCHEDULE` 或 `NO_COMBINATION`。|
| `GET /api/mini/v1/billing/?page=1` | 每页 10 张当前已发布结算单，仅本人。条目有 `id`、`invoice_no`、`visit_id`、`clinic`、`scheduled_start`、`published_at`、`revision`、`total`、`remaining`、`refund_due`、`review_pending`。分页返回 `page`、`pages`、`count`、`previous`、`next`。 |
| `GET /api/mini/v1/invoices/<id>/` | 从费用清单进入原有版本和记账明细。历史收费版本仍明确展示当前结算余额。 |

本人、代约和独立医疗授权各按原规则办理。小程序切换就诊人、退出或遇授权失效时，清空旧就诊人、费用、主行动、预览和查询结果，再按新范围读取。已有服务器版本缺少新增字段时，沿用原预约与就诊入口。

## 后续顺序与验收

1. 先验证合成患者从网页预约，同一编号在小程序可查。前台登记到诊后，两端刷新显示相同结果。本人费用可查，代约及其他账号隔离。用同一浏览器核对返回、窄屏及无号分支。
2. 用已有就诊、治疗、处方、发药、复诊和技工记录设计按就诊回查。明确医嘱开立、执行、结果审核与患者发布的责任，再新增通用检查报告能力。
3. 以诊所实际开放的科室与服务配置专业业务。扩科时再评审医师实体、资质范围、资源约束和迁移。独立体验版用关闭调试的手机实测找店、预约、到诊结果和费用。
