# v0.9-alpha.5：业务开发与验收说明

**父版本alpha.4；Mac迁移暂停；最后确认的运行实例仍为Windows v0.7。**
本轮交付源代码增量，不操作现有实例，不重排R4.4课程报告。

## 1. 为什么是基础目录

alpha.4已具备Clinic、Dentist、Qualification和DentistQualification模型，但没有相应的受控登记页面。仅依赖初始化演示数据，会阻断“新诊所/新牙医进入系统”的任务。本轮补齐资料登记和关联，不把人员入职、账号治理、专业审核和排程混成一个事务。

这是项目设计决定，而不是声称课件规定必须由技术人员维护人事资料：本课程合成演示暂复用现有SYSADMIN入口；现实机构应另行明确人事维护职责与个人资料最小可见范围。HQ/FINANCE/MANAGER/DENTIST/PATIENT/FRONT_DESK没有被自动扩大权限。

## 2. 已编码的操作

|目标|路径|保存范围|不自动执行|
|---|---|---|---|
|登记诊所|技术管理→基础资料目录→诊所|编码、名称、地址、主管联络姓名、电话、邮箱、面积|不授予任何账号主管身份，不建立出诊|
|登记牙医|技术管理→基础资料目录→牙医|员工编号、姓名、出生日期、联系地址、电话、邮箱|不生成登录账号、不授予DENTIST身份|
|登记资格类别|技术管理→基础资料目录→资格|编码、类别名称|不认证任何人的执业许可|
|登记/恢复关联|牙医详情→登记或恢复资格关联|DentistQualification关系/当前有效标志|不增加医学适配规则，不改预约|
|撤回误关联|牙医详情→预览撤回误关联|将原关联标为撤回，保留编号、备注和审计|不删除记录、不停用账号、不取消出诊|

编码仅接收大写字母、数字、短横线、下划线，以字母/数字开头，不把小写悄悄改成大写。并发检查既有同类编码；不会用新登记覆盖或复活停用记录。但不同编码指向同一自然人的重复资料仍须人工识别，本轮没有患者/牙医实体合并功能。

新目录记录默认可用，可能进入已有选择列表。账号登录、业务角色和出诊仍需分别办理；流程提示不是临床入职批准证明。

## 3. 确认与状态合同

所有写入使用：填写/选择 → 预览“尚未保存” → 再输入操作者技术密码 → 明确确认 → 同事务保存目录与审计 → 查询结果。
预览只读业务记录；预览时短事务可能获取关联行锁，不应被解释为服务器完全无技术副作用。
确认令牌绑定当前账号、工作上下文及其修订，期限15分钟。令牌是签名而不是加密，不应复制到公开渠道。[O1]

同次成功操作在令牌仍有效、当前权限仍成立时返回既有结果，不再写入；更换上下文、过期、撤权或停用后不得重放。结果未知先按原编码核对，不以换新编号的方式重做。

关联预览记录牙医/资格状态、原关联状态与最近关联事件游标。别人修改后即使又改回原值，事件游标仍使旧预览失效。撤回后恢复保留同一关联编号，原notes不会被此入口覆盖。

资格“有效登记关联”不等于专业资格当前有效：模型未包含执业地点、有效期、核验者、医学项目适配，本版排程也没有因此新增临床资质判断。

## 4. 接口与责任

|层次|文件|责任|
|---|---|---|
|纯领域规则|registry/directory_rules.py|字段白名单、编码/日期/面积格式、关联变更条件、签名载荷结构|
|业务服务|registry/directory_services.py|授权、预览、签名、行锁/协议锁、重复确认、保存与审计|
|表示层|registry/directory_forms.py、directory_views.py|字段错误、差异核对、明确确认、结果未知的恢复入口|
|导航与范围|workspaces/middleware.py、adc_core/context.py|精确路由角色限制与技术工作台入口|
|手动引导|guidance/catalog.py|只解释真实操作路径，不自动选择对象或提交|

使用现有UserAccount/WorkspaceContext授权协议，再锁定技术角色绑定。写命令加目录协议锁，关联按牙医→资格→关系固定顺序取行锁；各自不同资源操作之间仍须真实并发测试验证。数据库事务遵循框架atomic机制，已知重复键在事务边界外转成领域错误，不吞掉未知完整性错误。[O2][O3]

这是应用服务协议，不是对数据库owner任意SQL的保护承诺。

## 5. 本轮不做什么

不改旧诊所或牙医编码/身份信息，不停用或删除基础目录，不添加真实证件上传、有效期认证、人事审批、多资源CP-SAT、自动通知或支付。不得把这种有限登记界面称为“完整目录管理已完成”。Mac导出、恢复、ARM验证及交接全部暂停，已有工具只保留。

## 6. Windows上的下一步

1. 完整源码包解压到新目录；不要覆盖当前v0.7，不复制旧`.env`或数据库卷。
2. Docker Desktop本地Linux引擎就绪后，在新目录CMD执行`VERIFY_ISOLATED_WINDOWS.cmd`。
3. 检查本次`evidence/verification/gate-*.json`：每一步成功、all_gates_passed=true，脚本清理返回码也应为0。框架实际发现的测试数以日志为准。

该入口不使用本机Python；继承独立Compose和临时库。它会下载依赖并使用主机资源，但不使用原业务卷。不要用删除旧卷或SQLite替代来绕过失败。

绿灯后，在**合成数据副本**里人工验收：

|编号|动作|需要看到的事实|
|---|---|---|
|D1|技术管理登记新牙医，停在预览|目录和审计没有新增；页面明确尚未保存|
|D2|密码再验证后确认|一条牙医资料；未新增账号、权限或出诊|
|D3|创建两个资格类别并关联同一牙医|同一牙医有两个不同资格关联；未变更预约/账单|
|D4|撤回一个误关联，再按恢复依据恢复|同一关联编号，状态正确，旧记录与备注保留|
|D5|两标签/两个技术账号操作同一关联|旧预览拒绝；A→B→A仍拒绝旧预览|
|D6|重复确认同一有效请求|同一业务对象/事件，没有第二条记录|
|D7|切至主管/前台/牙医，直接访问目录URL|拒绝，不借同一账号其他身份放行|
|D8|只读实例查目录并尝试POST|允许受限GET；不保存；直接服务写调用也拒绝|
|D9|目录登记后另行办理账号和出诊|新牙医完成授权/出诊后能按原链条接诊；不是目录自动操作|

本轮不替你执行升级。累计包用于保存私密备份、带数据副本验证之后。不要发送密码、`.env`、API Key或真实个人资料。只发送合成测试日志或首个错误。

## 7. 之后的开发顺序

先跑当前候选真实数据库与HTTP测试、修失败，再补既有出诊的变更/停用影响预览与业务交接；然后才引入多资源占用和可靠通知。本轮不再把Mac迁移作为业务开发前置条件。
