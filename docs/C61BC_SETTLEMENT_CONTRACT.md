# C6.1B/C 原账单结算与资金核对

原实际费用 → 已核对资料 → 唯一模拟请求 → 原编号查询 → 独立分担复核 → 患者收退款 → 基金到账分配及撤销。

本文件细化 C61_LOCAL_INSURANCE_CONTRACT.md。费用分担、银行依据、基金分配、差异跟进及原单撤销已实现，冻结源码通过1,935项PostgreSQL回归。本地合成流程已通过准确CI、同镜像浏览器、容量、恢复和原系统保护更新；执行状态以[evidence_c61bc](evidence_c61bc/README.md)为准。正式报告按已实现功能描述业务，不把本地模拟解释为真实医保联网。

## 岗位及模块

| 办理事项 | 岗位 | 所有权与边界 |
|---|---|---|
| 原账单、实际收费行、接诊业务日 | 原诊疗模块 | 仅提供确切已发布版本的只读事实与公共锁操作；不生成治疗或改价 |
| 模拟请求与原编号查询 | 本店前台；财务可查询原请求 | 医保模块保留请求、逐行结果、原始模拟结果和追加历史 |
| 分担通过／未通过 | 不同账号的全链财务 | 重新核对来源及原办理人当前授权，不得切换岗位自行复核 |
| 患者现金收退款 | 原前台申请、财务独立审核 | 使用原现金账；申报和基金到账均不自动产生患者现金 |
| 基金到账、分配、退回依据 | 财务 | 财务模块拥有流水使用、核销和资金证据；医保不得重写 R1 匹配 |

患者代约授权不授予保险、病历或财务权限；主管和总部不获得患者结算明细。来源中的临床文字不进入医保投影或运行日志。

## 金额和状态规则

- 每条原收费行完整保留；现金责任＋个人账户＋基金＝原行金额，全部行汇总等于原账单总额。目录先自付只约束本行基金上限，不能解释成最终报销率。
- 缺少有效映射的收费保留自付例外；不能补造单位、待遇或抵扣。目录不能把一行的富余上限借给另一行。
- 只有独立通过的分担影响患者待收。处理中、回复未知、待复核、复核未通过均不代表清偿。
- 例：原账单 1000 元，明确模拟结果为现金责任 300、个人账户 200、基金 500。未收现金时待收 300；先收 100 时待收 200；原先已收 1000 时显示待退 700，由原独立退款流程办理。原收入一直为 1000，基金到账不会第二次计收入。
- 回复丢失保留 UNKNOWN；查询同一请求取得原结果。复核未通过仍保留外部模拟已受理事实，必须处置原请求，不能借未通过状态重复申报。
- 撤销沿原唯一请求办理，原结果未知须先查询。已确认分担在撤销待核对时保留，原未通过分担不产生抵扣；原撤销结果明确、净基金到账归零且无待审现金或分配时，另一财务账号才可确认终结。原账单、已收现金和收入不改写。

## 银行依据、分配与后续责任

原CSV流水和摘要继续由R1导入保存。同一流水在患者／设备现金匹配与基金凭据之间排他使用；基金凭据须经另一财务账号核对，不能复制一条流水形成两种活动用途。凭据保留收款或退回方向、金额、渠道、币种和依据，当前范围为CNY。

基金分配以一次1—100条明确申报和正金额提交，允许一笔银行到账分多批、一批对应多笔申报。已确认与待审分配共同预留银行和申报额度；复核通过再次检查来源、历史游标、权限及净余额，拒绝释放预留并保留决定。退回最多使用该申报原已确认净到账，不能先退待审款。原分配行、金额和独立决定不可覆盖。

未到账、短付、扣减和未知差异分别保留事项；未知金额为空，不写为零。事项必须有有效财务负责人和未来跟进期限，后续沟通、换人和结束追加事件。结束事项不自动改账，未解决差额不能通过自动向患者追收消除。

按整个批次排序获取原出诊、患者、就诊、账单和申报锁，再获取流水与分配锁；同一申报、银行流水和撤销在相同协议下重检。数据库约束另校验方向、同店／币种、额度、分配合计、独立复核与不可变历史。模块通过`insurance.fund_contract`和`finance.allocation_projection`交换限定事实，不互相改写记录。

账内四项总额、患者现金渠道对账、基金清算分别展示。日结中的基金应收按原实际接诊业务日归集；银行到账和退回按流水记账日展示。跨日到账不改原业务日，不重复记收入，也不阻断原内部日结。

## 一致性和失败后的继续办理

确认使用签名预览，服务端重读账单、目录、适配、最新待遇和现金历史。实际更正、收款、结算在同一 Invoice 行及原出诊／就诊锁序中串行核对。结算另外按既有患者、诊所、目录及适配锁序保护当前来源。失效预览要求重新核对，不产生部分请求。

同一账单只允许一个未终结请求。请求号、原费用、原始模拟结果、复核和事件保留；操作重放在重新授权后返回原结果当前状态。现金预览升级到 v3，包含结算历史游标，原 v2 写入令牌不再接受。财务仍能拒绝旧申请，不能因正向办理被阻止而留下无法拒绝的申请。

数据库校验原账单及诊所／待遇关系、逐行原费用、分担等式、来源上限、不同账号复核、唯一活动请求和不可重写历史。完整请求及行／结果／提交事件在一笔事务完成。权限和协议锁仍由业务命令执行，数据库所有者权限不是岗位权限。

| 问题 | 可观察行为 | 验证 |

| 新结算覆盖原治疗 | 确切版本与全部原收费行一致 | 数量／金额／跨店错误、历史不可改、事务回滚 |
| 基金到账与 R1 重复占用 | 同一流水下排他使用并分别核对分配 | test_fund_evidence：R1争用、重放、撤权与历史迁移 |
| 到账被分配两次或超额核销 | 银行及申报共同预留，独立确认 | test_insurance_fund_closure：同流水、跨流水、额度和SQL反例 |
| 差额无人负责或被默认为零 | 明确期限、换人、未知金额及追加历史 | test_insurance_fund_closure及HTTP表单 |
| 撤销重复处理或抹去原收款 | 原编号查询、基金退回后独立复核 | 撤销与分配并发、部分退回、UNKNOWN历史、患者现金保留 |
| 次日到账改变原收入或日结 | 接诊业务日与银行日独立汇总 | next-day数据库事实与daily_fund_summary |

全量回归、浏览器、七角色、独立金额核算、代表性容量、加密恢复、实际 ER、课程报告、准确提交 CI 和受保护本机更新仍是最终交付门槛。

思维导图：原费用 → {来源、待遇、逐行分担} → 唯一请求 → {未知查询、独立复核} → {患者现金责任、个人账户、基金应收} → 到账／退回／撤销 → 三类账务状态分别核对。
