# Windows：先隔离验证，再安排升级

当前源码为0.9.0-alpha.3；本机仍在运行v0.7。此说明不要求先部署中间alpha版本。

## 本轮立即执行的唯一入口

1. 下载**完整源码包**，解压到新的独立目录（例如桌面的ADC_engineering_v0.9a3）。不要覆盖原ADC_engineering_v0.3/v0.7目录，不复制`.env`、数据库卷或私密文件。
2. 打开Docker Desktop，等待本地Linux引擎就绪。在新解压目录的地址栏输入`cmd`并回车。
3. 执行：

```cmd
VERIFY_ISOLATED_WINDOWS.cmd
```

此脚本不调用本机Python。它用Docker镜像内的Python运行源文件与配置校验，因此不再依赖原先路径损坏的Windows Python Launcher。

## 脚本怎样隔离

- 只使用`compose.verify.yaml`，不合并`compose.yaml`。
- 新建随机`adc_verify_...`项目，核对当前Docker为本地context，拒绝远程host。
- 显式指定临时空环境文件，配置中使用合成测试凭据，不读取原应用`.env`。
- 测试数据库放在临时文件系统，无对外端口、无旧命名数据卷；仅把新源码目录`evidence/verification`挂载出来收集证据。
- 完成或失败时只清理本次随机项目，不执行`down -v`，不停止原ADC项目。
- 构建会从网络下载基础镜像/依赖，且会临时占用CPU、内存和磁盘缓存；独立验证不等于资源消耗为零。

不要将随机项目名改成原实例名，不添加原应用Compose文件或`.env`参数。如果已有同名随机项目/异常残留，停止并人工核对，不复用旧数据库。

## 如何判断结果

脚本末尾必须同时为：`Verification return code: 0`和`Cleanup return code: 0`。
在`evidence/verification`中找本次时间对应的`gate-*.json`，检查`all_gates_passed: true`以及全部步骤的returncode为0。同名`.log`保存过程。旧的绿色记录不能代表本次新代码。

完整门槛依次执行：372项基础方法 → Django check → 迁移差异检查 → 对**临时库**应用迁移 → 344项编写的Django/PostgreSQL测试。实际框架发现的数量仍以输出为准。此入口不包含真实浏览器E2E、Windows界面操作、生产TLS或恢复演练。

失败时只发首个错误与结尾摘要，或合成验证日志；不要发送`.env`、真实患者信息、密码、API Key。DNS/下载失败是环境阻断，不要因此随意换低版本依赖、跳过测试或改为SQLite。
Ctrl+C强制退出后，先用`docker compose ls`检查是否有该次独立项目残留；不得为了清理测试而删除原ADC卷。

## 隔离绿灯后仍要做

- 保存原源码（私密副本）及数据库备份；在副本上验证v0.7带数据升级。
- 已发布账单金额、账号、患者编号及候补历史应前后一致；备份可列目录不等于已恢复成功。
- 人工跑SU-26和旧主链，并核对实际后置条件；这个阶段才访问新版本网页。
- 当前`UPGRADE_V09_WINDOWS.cmd`需显式参数`--after-isolated-pass`才会继续，防止误点即停原服务。**参数本身不是测试证明**，只有取得上述实际证据后才使用。
- 累计更新包支持从原v0.7源文件集到本候选；本轮只完成文件重组验证，没有替用户执行升级。

## 可选：已有正常Python的环境

`python scripts/verify_isolated.py`提供跨平台主持脚本并导出host级结果；Windows用户优先使用上面的CMD入口。

## 功能验收路径

前台 → 选择诊所 → 患者档案 → 指定患者 → 更正联络资料 → 填写依据 → 核对差异（尚未保存） → 明确保存 → 查当前档案。
先用合成患者。用另一前台会话更新同一患者后，旧预览应被拒绝；只读实例应拒绝保存；已发布账单地址不随当前地址变化。
