# SU-31：按出诊核对关联业务并定位协调入口

需求基线：R4.4、SU-04/05/06/16/17、SU-29/30。候选实现：v0.9.0-alpha.7。Mac迁移暂停，原报告不重排。
本文件新增的是项目需求和设计决定，不代表老师课件指定了这些业务阈值或角色权限。

## 1. 用例规约

**主执行者：** 当前激活前台身份并选择了获授权诊所的前台人员。无辅执行者；不调用外部模型/通知平台。

**涉众利益：** 前台希望准确定位一条出诊的关联承诺，不在全店列表反复搜索；主管希望得到可重新核对的出诊编号与事实，而不是未经验证的“已清空”；患者希望已有安排只按本人明确意思和原业务规则变更，个人资料不过度展开；牙医希望已到诊/完成记录不因排班清理被撤销；维护人员希望错误关联不会导致越权披露。

**触发：** 前台依据已核对的人工协调需求，指定本店出诊编号或浏览有关出诊。

**前置条件：** 已登录且激活前台、已选择诊所。目标属于当前诊所、授权仍有效和资料完整性由本用例验证，不能预设“一定有待处理记录”或“已经允许停用”。

### 基本路径
1. 前台提供查询范围或明确出诊编号，请求查阅关联业务。
2. 系统验证当前身份和诊所范围，反馈匹配的出诊及定位所需统计；列表不是维护批准。
3. 前台指定一条出诊，请求核对其关联预约和邀约。
4. 系统读取原计划及完整有界的关联事实，检查诊所/牙医/患者关联、已接受邀约与正式预约的一致性，并计算读取时点下的阻断说明。
5. 系统反馈原出诊、牙医、时间、业务编号、分状态解释、读取时点、规则版本与原有授权办理入口。
6. 前台在必要时另行发起原预约/邀约用例；本用例不代替患者作决定，也不办理任何取消、改期或接受。
7. 前台在原办理返回后请求重新核对；系统重新读取，不根据刚才点击的按钮推测结果。若当前未发现阻断，反馈“可请主管重新核对”，主管维护仍另行核验。

### 扩展路径
- 2a/4a 当前角色错误、撤权、账号停用、诊所无权或上下文变化：拒绝，不借同一账号其他身份。
- 2b 查询参数无效：反馈字段错误，不退化成返回全店/全链资料；明确编号查询允许包含历史。
- 3a 目标不存在或属于他店：相同拒绝语义，不泄露该对象及患者详情。
- 4b 关联计数超每类1000条上限或检测到关系不一致：反馈需要受控核对；不展开可疑患者编号和深链，不用部分结果判断可维护。
- 4c 无关联业务：反馈当前未发现维护阻断；仍不是停用许可，查询后可出现新预约。
- 4d 已有预约或未过期待确认邀约：逐条核对；仅提供原流程，不批量办理。
- 4e 已到诊、治疗完成或无治疗关闭：作为受保护接诊说明，不提供快捷改期，不诱导为排班清空原记录。
- 4f 待确认邀约到期但未回收：按服务器时间说明已不再有效；不自动改变其存储状态。
- 4g 邀约已接受：核对直接关联预约及患者/时间一致性；不按旧确认截止将预约判作失效，不再计第二份保留。
- 4h 原出诊已开始或停用：反馈当前状态及历史，不提供维护批准或恢复入口。
- 4i 读取暂不可用：反馈本次结果未知，不推断前次写入失败，不自动重发。
- 6a 改期产生直接后继：原预约详情提供同患者同诊所的直接前后继和合法来源回跳，不能用任意URL/外店编号绕过授权。
- 7a 查询后又有新预约或其他变化：以新读取事实更新；原维护命令还须再次核验。
- 全程只读实例：允许获授权GET查询；保留原业务写入限制，不因新页面开放额外POST例外。

**成功后置条件：** 返回选定出诊在读取时点的受限关联投影及合法原业务入口；没有创建、更新、取消任何预约/邀约/候补/出诊/治疗/账单或授权，也没有发送通知或建立工单。

**最低保证：** 无权或不完整查询不被当作“无待办”；读取失败不改变原记录、不自动重放业务命令；患者个人资料不因主管地位较高而扩大可见；结果仅代表本次读取，不保证后续仍空闲。

**字段列表：** 输入为查询范围、出诊ID、页号；输出为出诊ID、诊所、牙医姓名及工号、原时间和状态、预约业务号/患者业务号、邀约与候补请求号、各自状态与起止/期限、关联预约ID、完整计数、读取时点、规则版本及受控内部入口。新列表不读取投影姓名、电话、地址、主诉、过敏或治疗正文。

**质量约束：** 窄屏和大字模式下主要动作可达；文字说明不能只依靠颜色；no-store防止浏览器重用旧响应，但不承诺清除用户此前已看见内容。两类关系各分页20项；判断不得只依据当前页。

**交互约束：** 前台工作台→出诊协调→按出诊编号核对。相关原详情带“返回出诊 #编号”；既有独立页面入口仍可用。主管仅获取聚合影响和告知前台的原出诊编号，本功能没有给主管创建前台入口。

## 3. 分析责任划分

- 边界：接收查询条件并呈现状态/下一步，不把点击理解为同意。
- 控制：组织授权、受限查询、完整性核对、来源链接和返回前复核。
- 实体事实：AvailabilitySlot为原供给；Visit为预约/接诊事实；WaitOffer与WaitRequest为机会及登记；不新建一张假的“协调完成”实体。
- 纯解释：front_coordination_rules接受值对象，不调用Django、SQL、AI或HTTP。
- 既有写责任：原预约和邀约services继续完成提交、并发防护、审计及回滚。本用例只把用户带到那些原边界。

本轮只建立当前查询视角，而非持久化工作流。每个前台操作的原业务事件并不自动等同于一份协调工单历史。

## 4. 关键不变量

对业务记录集合M，本用例自身要求 `M_after = M_before`；同时使用的会话、缓存头、日志、短事务与行锁是技术层副作用，不称整台服务器“完全零写入”。

`关联集合相同 + 同一读取时点` 才可比较派生结果；已接受邀约不会作为第二份有效保留重复计入。

`观察时无阻断` 不推出 `主管稍后提交必可停用`。

`coord_slot合法` 不推出 `拥有目标访问权限`。每个目标URL仍执行原授权，来源只用于导航。
