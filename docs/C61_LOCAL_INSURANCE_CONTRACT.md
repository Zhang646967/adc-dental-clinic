# C6.1 湖南目录与本地合成医保闭环

官方来源 → 地区版本与门店安排 → 本人及模拟待遇 → 实际费用 → 唯一结算请求 → 分担与患者清偿 → 基金应收、到账及退费。

本文件为医保增量业务合同。C6.1A资料基础已实现为源码候选，执行与交付核对见[C6.1A合同](C61A_PREPARATION_CONTRACT.md)；C6.1B和C6.1C仍须继续实现。当前已验收在用应用仍为C1-WX，真实微信、医保机构和云端条件均未提供。本阶段只使用合成身份及明确的本地模拟结果。

## 业务问题与边界

当前账单与独立收退款可以核对内部资金，但尚不能表达医保目录版本、模拟待遇、个人账户和基金承担。C6.1分三个连续增量交付，先完成可核对的资料基础，再接入真实费用及分担，最后完成基金到账与撤销。准备功能不会被写成资金闭环已完成。

湖南官方通知规定口腔项目支付政策自2026年6月1日起执行。甲类的目录先自付为零仍须按基本医保分担，不能解释为患者一律报销100%；乙类先自付与最终基金承担是不同字段。[官方通知](https://ybj.hunan.gov.cn/ybj/first113541/firstF/f3113607/202603/t20260331_33945644.html)

已保留附件原字节及摘要。附件虽名为docx，实际为OLE Word；口腔表232行中202个不同编码，30行完全重复，没有冲突重复。编码013105010310000的支付分类及先自付两格为空，经原表渲染核对仍为空；继续标记UNKNOWN，不能填零或纳入自动分担。202个编码包含变体，不称为202项基础诊疗操作。

源表另有两条单位为空。资料准备保留空值，不从父项目或名称自动继承单位；收费映射时须明确核对。目录准备不修改实际收费数量或价格。

## C6.1A 目录、门店安排与模拟待遇

1. 版本保留地区、通知、生效日、原文件、解析版本、摘要及全部原始单元格。导入先预览，合法重复明确跳过，冲突或无效批次不部分接受。目录发布须经另一账号的财务核对；原版本和决定保留。
2. 门店主管准备本店课程医保安排，财务独立确认地区、有效期和适用范围。页面始终显示“课程模拟安排”，不显示为真实医保定点资格。当前患者所处城市不能替代参保地。
3. 本店前台登记明确患者的合成参保地、参保类型及模拟待遇核验依据。患者自填“已参保”或C1手机号来源不等于待遇核验。原本人与代约授权不因医保资料而扩大。
4. 实际收费编码与医保编码显式映射，不按名称模糊合并。收费单位、数量及项目含义不相容时继续待核对。目录和映射不改价格、治疗、原收费行或旧账单。

完成门槛：目录字节及202条规范记录可追溯；UNKNOWN保留；同店权限、独立复核、版本竞争、停用和有效期正确；准备步骤产生零资金与治疗事实。ER仅在实际追加迁移后生成，保留现有54份迁移原字节。

## C6.1B 实际费用与唯一模拟结算

1. 从原发布账单的确切版本和实际执行收费行选取申报，不另造治疗或拆分原价格。预览保留逐行单位、数量、目录、先自付及未知原因；没有可核对映射的行不生成基金承担。
2. 模拟适配器持有唯一请求编号及本地结果。请求、处理中、结果未知、已确认、已拒绝和已撤销分别记录。网络丢失成功回复时先查原编号，不能用新编号重复结算。
3. 财务以不同账号复核最终分担。账单金额等于患者现金责任、个人账户承担及基金承担之和；该等式不是“已收到现金”。本地例子逐笔保存明确模拟结果，不硬编码全国或湖南统一报销比例。
4. 已确认个人账户及基金承担影响患者待缴投影；待处理或未知结果不当作清偿。未知期间的新收退款及相关费用更正须先解决原请求，防止患者重复支付或审批旧预览。
5. 原患者现金收退款保持原资金账及独立审核。患者余额、原账单收入、实际现金、个人账户承担和基金应收分别展示；基金到账不能再次增加收入。旧账单与旧资金历史不回写。

完成门槛：收款前分担、已自付后转模拟医保、部分付款、结果丢失、同次重试、撤权、并发确认和账单版本变化均可办理或明确继续；1000元示例的各来源及余额由数据库独立计算。

## C6.1C 基金批量到账、争议与退费

基金承担形成独立应收，银行到账和逐笔分配另行确认。一笔银行流水可分配多笔申报，但分配合计不能超过到账，单笔申报核销不能超过当前有效应收。扣减、争议和未到账保留，不自动加到患者账上。

原R1只支持一条流水对一笔现金记录，继续保留这一适用边界。基金批次通过定义清晰的财务资金证据占用及分配操作接入，R1和基金业务在同一流水锁下核对唯一使用。保险模块不直接改写R1匹配或资金行；数据约束与原子重检共同防止跨渠道重复使用，不能通过制造平衡分录凑账。

撤销先查询并明确原外部模拟结果，再核对已核销、已退回及患者已收付。资金确已到账时须保留相应退回或冲销依据；患者退款仍走原独立审核。未知和部分完成显示原进度，不把撤销请求或退款申请称为全部完成。

账内日结、渠道对账和基金清算是三个状态。基金次日或后续到账不改原业务日期，不阻断已有四项账内日结；新增投影明确哪些金额尚非现金。

## 模块合同与交付验证

医保模块拥有目录、门店模拟安排、模拟待遇、申报及结算历史；原诊疗拥有实际执行，原开单拥有收费版本，财务拥有收付、证据占用、银行到账及核销。模块以明确命令和只读投影协作，不跨模块直接更新状态。继续使用Django、PostgreSQL和既有事务／工作进程，不引入新外部REST接口或微服务。

验收追踪至少覆盖：目录缺失、重复冲突、单位不匹配、参保地与定位不同、门店停用或非生效日、跨店与代约范围、自己复核、旧预览、并发与重试、个人账户和基金非现金、同一流水被R1与基金争用、部分核销、未知状态撤销及原资金退款。

每个增量完成全量回归、实际PG权限／并发、真实浏览器及数据库核算，按准确提交CI和已验收镜像交付。完整金融增量再执行代表性容量及包含新表、原文件和分配历史的加密独立恢复。本机更新前后保留原账号、患者、诊疗、资金及配置。正规报告说明业务及已实现状态，工程过程放在证据目录。

思维导图：来源与版本 → 门店安排与参保信息 → 原实际费用 → 唯一请求及独立分担 → {患者余额、个人账户、基金应收} → 到账分配／撤销退费 → 分别核对账内日结和渠道清算。
