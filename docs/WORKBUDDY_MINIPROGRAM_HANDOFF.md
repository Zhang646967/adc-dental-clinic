# WorkBuddy 小程序部署交接

微信身份 → ADC后端会话 → 本人／授权就诊人 → 原预约业务；WorkBuddy仅负责小程序部署。

## 1. 交接结论

用户最新要求：优先真实微信登录，小程序不再出现模拟手机号登录或绑定步骤；WorkBuddy只负责小程序部署，系统开发、后端认证、数据库与服务器由主系统维护方继续负责。

已完成客户端整改：微信为主入口；模拟短信能力不产生手机号登录入口，也不能由页面方法申请／消费模拟验证码。账号页不再展示本地合成手机号及本地恢复凭证操作。只有后端明确提供真实短信能力时才显示可选短信方式；手机号不是微信登录前提。原账号密码作为开发联调及旧账号关联的备用方式，现有账号和历史不重置。

**真实微信尚未验收。** 本次核验发现：可见工程及私有配置已有注册AppID；私有配置缺少配套AppSecret；运行中的本机后端为`auth_mode=demo`、未加载AppID/AppSecret、`sms_provider=demo`，因此`auth_capabilities.wechat_mini=false`。不是小程序发布后自然就能修复的问题。不得硬改能力为true、伪造微信身份或用测试手机号冒充真实授权。

## 4. 真实微信登录：后端依赖与接口

已有业务路径：用户主动同意 → `wx.login()`取得一次性code → ADC服务端用配套AppID/AppSecret调用`code2Session` → 微信身份映射到ADC账号 → ADC签发自己的会话。

登录不要求预先绑定手机号或填写身份证；微信身份不等于患者档案、监护关系或员工权限。新微信账号没有既有就诊权限时进入“我的账号”办理档案关联／核验，这不属于登录失败。不要为使页面跳转顺利而自动创建病历或放开授权。

| 现有接口 | 约定 |
|---|---|
| `GET /api/mini/v1/session/` | 初始化Cookie、CSRF、认证能力与当前账号／就诊人上下文；先核对`auth_capabilities.wechat_mini` |
| `POST /api/mini/v1/auth/wechat/` | 表单`code`、`confirmed=on`；原账号关联时才附加原`username/password`，正常首次／重复微信登录二者为空 |
| `POST /api/mini/v1/account/wechat/bind/` | 在已登录ADC账号中重新取得微信code后明确绑定，复用现有账号上下文 |
| `GET /api/mini/v1/account/` | 自有账号及档案办理状态；不自动扩张患者权限 |
| `GET /api/mini/v1/patients/`／`POST .../patients/select/` | 就诊人切换沿用原授权及版本规则；不能依据微信昵称或手机号自动代约 |
| `POST /api/mini/v1/logout/` | 清理ADC会话及客户端内存上下文 |

客户端已有`utils/api.js`负责Cookie和`X-CSRFToken`、`X-ADC-Workspace`、`X-ADC-Account`。响应沿用`{ok:true,data:...}`，错误包含业务提示及可能的`request_id`。不要用本地存储中的固定OpenID、伪造Token或自建另一套登录替换它；AppSecret和微信`session_key`不进入客户端。

私有输入在：`/Users/zhang/Downloads/ADC系统试用/WX1私有配置.env`。AppSecret由用户私下填写，主系统维护方负责按`docs/WX1_GUIDE.md`应用并重建后端。真实认证采用`ADC_PATIENT_AUTH_MODE=live`、`ADC_PATIENT_IDENTITY_PROVIDER=disabled`；未开通真实短信时`ADC_SMS_PROVIDER=disabled`。业务资料仍为合成数据，与身份认证模式分别管理。

WorkBuddy发现`wechat_mini=false`时回传“后端认证未准备好”，等待主系统维护方处理；不可自行改后端环境、强开按钮或补模拟手机号步骤。个人主体的微信取手机号组件继续保持关闭，除非以后另行核验权限并授权开发。

## 5. WorkBuddy执行顺序

1. 先校验交接包摘要，导入其中“微信小程序”目录。保留已有AppID，不使用其他示例AppID，也不索取AppSecret放进工程。
2. 本地模拟器使用`mode=local`、`http://127.0.0.1:18000`。核对20家门店、登录页无测试手机号／页面验证码、原账号可作为本地备用方式。不能将这一步写成真实微信通过。
3. 微信后台核对实际主体、类目、备案、接口权限和体验成员，记录实际状态；不承诺个人主体自然满足医疗类目或公众发布要求。
4. 等主系统维护方提供已验证的HTTPS地址及微信能力就绪结果后，再生成`mode=experience`工程，启用`setting.urlCheck=true`并核对实际请求域名。`development`与关闭域名检查只用于明确标注的开发调试。
5. 本人扫码登录开发者工具，编译、预览和部署教师体验版。未获明确指示不提交公众正式发布，不购买云资源、短信或付费服务。
6. 先验证真实微信登录，再验证选店选医、本人／监护就诊人、预约、改期、候补与本人结算单；写入测试仅在主系统维护方提供的独立合成测试库办理，不能在原18000为验收批量造业务记录。
7. 按下方验收清单回传，保留未完成状态。需要代码修复时提供复现和查询编号，交由主系统维护方处理。

需要生成体验工程时由主系统维护方提供准确源码版本并使用现有生成器：

```sh
python3 scripts/prepare_wechat.py --mode experience --appid '已核对的AppID' \
  --api-base 'https://已核对的固定域名' --output '/一个新的体验工程目录'
```

不要把`127.0.0.1`、过期预览码或旧临时域名作为老师手机端的部署成果。

## 6. 接收与回传标准

- 本地：官方工具实际编译／运行、20店可浏览、模拟手机号／合成号绑定入口不存在、原账号备用登录可用。
- 真实微信：至少两个真实微信账号首次、重复、退出后登录，映射不串号；拒绝授权、过期code和重复code不产生伪造会话；不需要手机号即可完成微信账号登录。
- 账号／权限：原账号明确核验后关联，不自动合并；登录成功不跳过本人档案或监护核验；患者及代约人维持原临床／账单边界。
- 体验版：正常域名校验开启、教师已获体验权限，实际手机可打开与办理；记录机型、系统、微信版本及包版本。工具、预览、真机、体验和正式发布分开记录。
- 回传：代码提交、工程／包摘要、后台权限结果、域名模式、设备记录、逐项PASS／FAIL／BLOCKED及证据。失败提供页面路径、脱敏错误、`request_id`及复现步骤，不回传密码、手机号、code、OpenID、Cookie、Token或密钥。

未收到AppSecret、固定HTTPS或平台权限时，相应项为`BLOCKED_CONFIGURATION`，其他已完成部署准备可以交付；不能写成“真实授权登录完成”。

思维导图：主系统维护方提供认证与业务API → WorkBuddy负责工程配置／编译／预览／体验部署 → 用户完成平台授权 → 真实微信与手机验收 → 问题回传主系统维护方。
