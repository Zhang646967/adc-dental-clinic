# SU-29 / SU-30：出诊安排的受控变更与停用

需求基线：R4.4、SU-19新增出诊、SU-27/28基础目录。候选实现：v0.9.0-alpha.6。
本文件是项目新增需求和设计决定，不代表教师课件指定了这些岗位、期限或上限。R4.4报告未改动。

## 业务目标及范围

主管需要纠正未来出诊计划，又不能借一次排班修改改变患者已经取得的预约机会。此增量只处理尚未开始、无有效业务占用的原时段；已有业务先协调，再重新判断。不是自动换牙医、批量搬迁患者、停诊应急调度或完整业务交接系统。

单纯改写AvailabilitySlot.starts_at/ends_at，会使仍引用原时段的历史预约看起来属于另一个计划。本轮选择保留原记录的时间、牙医及诊所，以停用旧记录和创建替代记录表达调整。

## SU-29 调整未来空闲出诊时间

**主执行者：** 当前激活MANAGER且已选择诊所的诊所主管。无辅执行者或外部AI。

**涉众利益：** 主管希望明确出诊安排和变更影响；患者希望既有预约或有效邀约不被暗中取消、改期；牙医希望历史出诊和接诊责任可核对；前台希望业务协调与排班维护职责分开。

**触发：** 主管依据已核对的计划提出时间调整。

**前置条件：** 会话有效，当前工作身份为主管且已选店。是否授权、是否空闲、是否尚未开始以及是否冲突由本用例检查，不把它们全部预设为已满足。

**基本路径：**
1. 主管指定本店原出诊，请求查询安排及相关业务影响。
2. 系统核对当前身份与范围，读取原时段、相关预约与邀约的必要事实，反馈时间、牙医、诊所、占用数和读取时点。
3. 主管提供新的开始、结束和固定类别的依据，请求预览变更。
4. 系统检查原记录及关联事实未在填写期间变化，原时段未开始且有效，没有阻止变更的业务，新时间在未来且不与同牙医其他有效出诊冲突；反馈新旧时间、历史保留方式及未发布草案影响。尚不保存。
5. 主管核对影响，明确要求保存。
6. 系统再次检查当前权限、上下文、确认期限、源对象与关联快照，并检查当下占用和时间条件。在同一事务中停用原时段、创建同店同牙医的新时段并记录两者关联及审计。
7. 系统反馈原记录及其替代记录入口，供主管核对已保存事实。

**扩展：**
- 2a 对象不存在、诊所不符、账号/角色/范围失效：拒绝，不暴露患者资料。
- 2b 原时段已开始、已结束或已停用：拒绝本轮修改，保留历史。
- 2c 有SCHEDULED、CHECKED_IN、COMPLETED或CLOSED_NO_TREATMENT记录：拒绝；未闭合业务由前台协调，已完成业务不能为排班调整而取消。
- 2d 有PENDING且expires_at大于核验时点的邀约：拒绝，待患者决定或到期后重新核对。
- 2e 记录关联不一致或任一关联集合超过1000条：不以部分结果认定空闲，提示受控核对。
- 4a 开始不在未来、结束不晚于开始、包含秒/小数秒、新旧时间完全相同：指出问题，不生成可执行确认。
- 4b 相同牙医在其他有效时段有重叠（包括跨店）：拒绝，不透露其他诊所患者信息。
- 4c/6a 旧页面或旧快照：拒绝。即使相关事实后来又变回相同值，新增审计/关联记录仍使旧快照失效。
- 5a 主管放弃：不保存。
- 6b 预览之后有人预约或发布有效邀约：以本次锁定后事实为准，本次调整不执行。
- 6c 同一成功操作在有效期和当前权限内重复提交：返回原结果，不再创建替代时段；不恢复此后又被合法停用的替代记录。
- 6d 新时段并发冲突、保存或审计失败：回滚本次停用和新增，原有效安排保持。
- 6e 网络回执不确定：先查询原时段与维护记录，不推断原操作失败，不自动重试。

**成功后置条件：** 原时段is_active=False，但原编号、时间、诊所和牙医保持不变；新增同店同牙医的一条有效时段；维护事件将两者关联；未改动任何Visit、WaitOffer、WaitRequest、Patient、Invoice或账号授权记录。

**最低保证：** 失败不留下“原时段已停用但替代时段缺失”的部分结果；历史记录不删除，已保存的既有业务不改变。重复请求不撤销先前成功结果。

**字段列表：** 源出诊编号、新开始、新结束（北京时间、分钟精度）、固定依据类别、源快照令牌、预览确认令牌、当前工作上下文、操作编号、明确确认。

**交互约束（不混入基本路径）：** 主管工作台→出诊安排→查看安排与影响→调整未来空闲时段→预览影响→确认出诊变更。大字模式、键盘及无脚本文本路径保留；新时间控件动态提示结束下限，但服务端始终复核；不会静默重写用户结束时间。

## SU-30 停用未来空闲出诊

**主执行者：** 当前店主管。

**涉众利益：** 主管需要停止提供某条未来机会；患者不希望预约被无声删除；审计与运营需要保留原安排依据。

**触发/前置：** 主管提出停止某条原时段；有效会话、当前主管身份与诊所已选择。空闲性、有效性和授权由系统核验。

**基本路径：**
1. 主管指定原出诊并请求停用影响预览。
2. 系统以与SU-29相同的权限、状态、未来时间、关联一致性与占用规则核对原记录。
3. 系统反馈原安排、停用影响和已核对的依据；尚不保存。
4. 主管明确要求保存。
5. 系统重新核验预览、当前授权与占用，在同一事务中将原记录is_active置为False并记录审计。
6. 系统反馈原记录当前状态和历史入口。

**扩展：** 引用SU-29的授权、已开始/已停用、占用、旧页、上限、重复、失败和未知结果分支。停用不得携带新的开始/结束时间；不存在借停用动作更换牙医或诊所的分支。牙医资料已停用时，只要当前诊所授权仍有效且原出诊满足无占用/未开始条件，可以停用，但不能新建替代时段。

**成功后置条件：** 只停用原出诊并新增审计。旧编号和全部关联历史保留，没有新增替代时段、预约或邀约。

**最低保证：** 校验失败或审计失败不使部分操作生效，不取消任何正式预约，不自动回收邀约，不删除原记录。

**字段：** 源出诊编号、固定依据类别、状态/确认令牌、当前上下文、操作编号、明确确认。无新时间字段。

## 业务规则与实现追踪

|规则|内容|实现与验收入口|
|---|---|---|
|BR-A01|当前角色+当前诊所，不借账号其他授权|require_availability_actor；HTTP与服务正反矩阵|
|BR-A02|只维护未开始有效时段；有占用先拒绝|block_reasons/validate_replacement；预约/到诊/有效邀约分支|
|BR-A03|原记录不改时间；调整生成新记录；不删除|confirm_availability_change；历史字段与ID核对|
|BR-A04|预览不承诺资源；最终重新检查|源槽行锁和已有排他约束；预约/发布/新增出诊竞争|
|BR-A05|预览与确认分别绑定主体、对象、上下文、期限和状态|state/proposal两个类型，签名15分钟；错主体/过期/ABA|
|BR-A06|重复成功操作不重复写入；失败原子回滚|AuditEvent操作编号；失败注入/两连接竞争|
|BR-A07|有效邀约按时间判定；草案不是占位|到期未回收不阻挡；旧草案发布拒绝并提示重生成|
|BR-A08|只读实例不保存，主管只见协调统计|HTTP策略+require_writable；无患者姓名/主诉/联系方式输出|

测试：`checks/test_availability_rules.py`为纯规则/源码合同；`tests/test_v09_availability.py`为真实PostgreSQL与HTTP待执行测试；`scripts/check_availability_browser.py`为合成静态模板检查。三者不得互相替代。

## 分析与设计说明

- 边界责任：接收时间/依据和明确确认，反馈差异与恢复入口。
- 控制责任：组织预览及最终提交、权限、锁顺序、重复结果与审计。
- 实体事实：AvailabilitySlot提供原计划；Visit和WaitOffer提供已承诺业务事实；AuditEvent提供维护关联和事件游标。
- 查询与规则分开：纯规则模块只解释给定事实，不操作数据库，也不调用AI。
- 替代关系暂保存在维护审计中，而非新增计划版本表。不能将其称为完整的排班版本管理或数据库层强制的替代外键。
- 共同锁协议的范围是应用服务：普通预约、发布、接受和维护均先锁原AvailabilitySlot行。数据库owner任意SQL不在这一协议保证内。
- 本轮不提供完整前台协同工单、自动患者通知、行政停诊处置或医生责任交接；提示与导航不是已经自动完成业务交接。
