# C1.1 患者关系与预约代办合同

本次采用模块化单体，在 portal 内集中管理患者选择与预约授权；原 PatientAccess 本人绑定保留。联系人、亲属关系、登录账号、预约代办、病历访问和知情同意分别处理。技术管理仅分配核验职责，不代替工作人员进行关系核验。

## ADR-C1-IDENTITY / PROFESSIONAL

本店前台受理关系，已有前台岗位通过明确的 `can_verify_patient_relationships` 职责授权后才能核验。核验记录办理人、依据类型、内部依据编号、说明和有效期。父母、监护人、患者委托人可获本店预约代办范围；联系人和其他亲属的关系记录本身不产生授权。受理时可无账号，核验代约前须人工确认具体账号归属，不按手机号或姓名合并。角色仍为七种，本阶段不证明医疗专业资质或法律监护资格。

授权仅包括所选患者在核验诊所的预约查询、新约、改期、取消和候补；不包括诊疗记录、账单、支付及临床知情同意。账户可以有本人入口及多个经核验的代约入口。网站和小程序显式切换患者，服务端上下文递增版本，旧表单作废。授权暂停、到期、撤销不取消原约，由前台继续协调。暂停后重新核验追加决定，旧预览不得复活。

## ADR-C1-RECEIPTS

新增关系受理、预约授权、追加式关系事件三张表。BookingReceipt 保留原本人 FK，增加授权 FK，数据库约束恰有一个来源；历史回执不改写。上下文保留所选授权。签名预览绑定实际操作账号、患者、授权版本、工作上下文和操作编号。确认时重新锁定用户、上下文、关系、授权，再调用现有预约锁序与资源命令；同一患者的多个合法操作者共享原患者/资源互斥。

关系事件由 PostgreSQL 阻止更新和删除；逆迁移对已有新业务事实拒绝破坏性回退。业务授权依据由命令验证，数据库约束负责来源唯一、有效期和历史保护，不宣称数据库管理员无法绕过业务命令。

## ADR-C1-CLINICAL-MONEY

关系核验、授权和患者切换不产生治疗、应收、现金或同意记录。代约页面与 API 不返回既有临床文字、账单详情。新预约意向仍由预约命令记录，实际诊疗与收费由原有流程负责。运行日志不写联系人、核验依据和临床文字。

## 需求与验收

| 编号 | 岗位和行为 | 不变量及失败回应 |
|---|---|---|
| C11-01 | 前台受理、核验、补账号 | 同店患者可见；仅明确核验职责可决定；联系人无授权 |
| C11-02 | 患者/代约人选择就诊人 | 不按手机号合并；仅有效授权清单；切换旧预览失败 |
| C11-03 | 双渠道预约与改期 | 同一资源唯一有效结果；回执有实际操作来源；重试不重复 |
| C11-04 | 候补登记/邀约/退出 | 共享原候补与改期命令；不自动接受或取消其他预约 |
| C11-05 | 前台暂停、撤销、重核 | 立即阻止新确认；保留原约与历史；旧授权版本不复活 |
| C11-06 | 账单、病历、跨店隔离 | 代约不能扩大临床/资金权限，服务端拒绝越权 |
| C11-07 | 数据与交付 | 原迁移和历史不改写；新表真实 ER、独立恢复、准确提交 CI |

测试执行与未执行边界单列于 C1.1 交付证据；本合同不作为执行通过证明。
