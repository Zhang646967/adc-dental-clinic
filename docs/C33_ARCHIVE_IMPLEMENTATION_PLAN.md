# C3.3 病历归档与受控复制实施规格草案

文书完成 → 缺项处理 → 独立审核 → 准确版本归档 → 追加补正 → 身份核验与副本交付。

状态：A批员工侧归档与追加补正已实施，完整发布结果见`docs/evidence_c33a/README.md`；B批受控复制仍为下一阶段设计。实际结构已追加至77份迁移、163张SQL表、41个ER视图，保留全部原迁移与历史。WorkBuddy既有费用与医疗决定结果不重复执行。

## 1 依据与业务目标

电子病历规范要求保留操作者及操作痕迹，并区分归档状态；归档后特殊修改需要医务部门批准和痕迹。这支持“固定原包、追加补正”的设计。[电子病历应用管理规范第14—17条，政府转载](https://www.beijing.gov.cn/zhengce/zhengcefagui/201905/t20190522_59868.html)

病历保管、复制受理和申请人材料核对有专门职责，不能把普通预约授权扩为整份病历权限。[医疗机构病历管理规定2013年版第5、17—21条，政府转载](https://www.fxtp.gov.cn/content/2023/797639.html)

复制范围设计同时核对后来的条例，涵盖患者依法可查阅、复制的病历资料和医疗费用，不能只照旧版示例列表编码；缺少系统内资料应明确说明。[医疗纠纷预防和处理条例第16条](https://www.beijing.gov.cn/zhengce/gwywj/201905/t20190522_61432.html)

以下岗位分工、审核独立性、在线交付及批次是ADC的设计选择，不冒充法规逐字要求或真实机构已通过的制度。继续使用课程合成资料；真实专业审定与可靠电子签名分别验收。

思维导图：真实文书 → 可追溯操作者 → 归档状态 → 原包固定 → 追加补正与合法复制。

## 2 A批 归档与追加补正

### 岗位与办理

| 责任 | 业务行为 | 边界 |
|---|---|---|
| 负责医师 | 完善文书、处理责任待办、提交准确归档清单 | 不能以自己的另一岗位完成独立审核 |
| 明确获委任的医务审核医师 | 核对本店及服务范围内完整性、批准归档和归档后补正 | 专项职责默认关闭，不从主管或技术岗位继承 |
| 前台 | 查看“待完善／待审核／已归档”及责任期限，联系协调 | 不获得临床正文或医务审批权 |
| 总部与主管 | 汇总数量、逾期及责任趋势 | 不读取跨店临床包或批准医疗内容 |

接诊结束、账单发布、付款结清和归档分别保存状态。待归档不继续占用椅位，未结清费用不作为软件阻止归档或提出复制申请的条件。归档不补造实际治疗或收款。

归档清单绑定已确认的病历文书、检查与治疗方案、具体告知及本人／适格代理决定、开治／实际治疗、真实补记及复核，以及选定的费用版本。没有发生的治疗不生成空白“已签署”记录；无治疗、分次治疗和已确认阶段不另收费分别表达。待确认文书、未完成的必要审核或来源变化返回具体岗位及继续入口。

已发生治疗但缺事前依据时保留真实缺口；独立复核不变成事前通过。首批不以“已复核”自动越过必要材料要求。不能补回的缺项转医务处置，可保留现有材料的保全清单，但不标为正常完整归档；特殊例外需另行明确机构规则。

### 固定证据

归档前预览清单、版本和缺项。明确提交后由另一名有职责的医师核对；确认时事务重检来源游标、版本、待办及职责。后台生成固定PDF与清单，保存内容字节摘要、渲染版本和时间。摘要证明文件一致性，不等于可靠电子签名。

生成失败保留待生成任务与原因，不假报归档；重试复用原任务。来源在审核或生成期间变化，要求重核，不把后来内容塞进旧清单。只有文件、清单和审核证据均就绪，才发布归档回执。历史图片、姓名及机构资料用当时快照，不跟随当前目录变化。

归档后更正先说明原因、差异和来源，由不同医务审核人批准，再允许临床模块追加更正版本并生成新版归档包。旧文书、旧包、旧审核和交付记录保留。新一次就诊正常建档，不要求为了继续治疗而“解锁旧病案”。归档后的真实授权撤销、同意撤回或财务更正不被删除：原模块继续保留事件，归档模块登记后续关联，不重写旧包。

### 模块责任

临床模块拥有病历、方案、告知及真实执行；财务模块拥有收费与资金；归档模块只持有审核、来源清单和固定文件。临床追加操作通过明确定义的归档补正核验入口，不能直接改归档表；归档不能直接改临床或资金行。历史费用包绑定准确收费版本，不误调用“当前余额”重绘旧包。

思维导图：文书及真实事实 → 缺项与责任 → 独立医务审核 → 固定文件 → 归档回执 → 原包保留与追加补正。

## 3 B批 患者申请与受控副本

先支持本人在线发起申请及审核后下载。预约代理、现有指定步骤医疗代理均不自动获得整份病历复制权。监护或书面代理的副本申请需要另行核验本用途、范围及期限，不能借读取状态获得正文。前台可有默认关闭的材料受理职责，仅看必要身份、材料编号与办理范围；医务审核查看具体内容和批准范围。

申请指定患者、诊所、就诊或文书范围、用途、接收人及所需版本。状态为“待材料核对→待医务审核→待生成→可领取→交付请求已记录”，另有退回、撤回及拒绝；下载链接到期不删除申请或归档资料。空范围、缺失文件、跨店或授权撤销给出明确结果，不扩大范围兜底。

副本只从获准的固定清单生成，包含来源、准确版本与必要完整性信息。账号及授权在每次下载时重检，文件不放公开静态目录，不使用任何人持链接即可读取的地址。撤权、停用、换账号或过时预览均不能继续领取。下载成功记录服务端已返回文件，不推定患者阅读、纸件盖章或可靠签名已完成。

归档、复制与争议保全分别建模；日常归档不冒充法定共同封存。第一批不自动办理司法调取、患者死亡后主体资格或封存启封，也不自动删除到期病历。政策期限、机构保管制度和真实交付手续在专业试点前另行核验。

思维导图：申请人身份 → 本用途与范围 → 材料核对／医务批准 → 准确副本 → 每次领取核权 → 交付请求与历史。

## 4 需求到验收

| 编号 | 具体场景 | 验收结果 |
|---|---|---|
| AR-01 | 正常完成诊疗但未付清 | 文书合格时可归档，原应收不变 |
| AR-02 | 无治疗／阶段不另收费 | 如实保留结果，不补治疗或资金 |
| AR-03 | 必需文书或核对缺失 | 返回责任、原因与继续入口，不假归档 |
| AR-04 | 自审／主管／跨店审核 | 拒绝；专项职责不自动授予 |
| AR-05 | 审核后来源变化／并发确认 | 旧预览失效，只产生一个准确包 |
| AR-06 | 文件生成中断后重试 | 不重复发布，失败状态可继续处置 |
| AR-07 | 归档后目录、金额或后续就诊变化 | 旧包字节与清单保持，后续事实另存 |
| AR-08 | 已归档更正 | 另一医务人员批准后追加新版，旧包仍读 |
| CP-01 | 本人申请选定范围并领取 | 文件范围、来源和版本一致，交付留痕 |
| CP-02 | 仅预约／步骤医疗代理 | 不能读整份病历或取得复制权限 |
| CP-03 | 审核或领取前撤权／停用 | 拒绝新领取，原申请和交付历史保留 |
| CP-04 | 缺文件／越权编号／换账号 | 明确提示，不泄漏其他患者内容 |
| CP-05 | 重复下载与网络中断 | 不改原包、不产生收费，不误判已阅读 |
| AR-09 | 加密恢复到空库 | 文件字节、清单、审核和副本历史一致 |

A批先交付员工侧归档和补正；B批再给WorkBuddy本人申请、进度与只读领取场景。每批先运行相关真实PostgreSQL及并发检查，完整发布时统一回归、恢复和保护更新。新增表采用追加迁移，实施后再从真实PostgreSQL生成ER，不用本草案替代现有实际图。

思维导图：规则与职责 → 准确来源 → 异常与并发 → 固定文件 → 领取隔离 → 恢复验证 → 专业与平台分别验收。
