# v0.9.0-alpha.6：开发与验收说明

父版本alpha.5；报告仍为R4.4；Mac迁移继续暂停；用户最近确认运行基线仍为Windows v0.7。本轮没有连接或修改该实例。

## 1. 本轮要解决的问题

系统原来只能新增出诊，无法让主管从既有安排查看影响并受控调整。不能通过直接改原起止时间、删除原时段或批量取消预约来填补这个缺口。

新增SU-29（调整未来空闲出诊时间）、SU-30（停用未来空闲出诊），以清楚的业务边界支持下一个运营闭环。原SU-19新增出诊继续保留。

## 2. 操作路径与可见结果

主管工作台→先选择诊所→**出诊安排**→选定原记录→**查看安排与影响**。

详情列示完整北京时间、牙医、当前状态及关联预约/邀约统计。只提供协调统计，不显示患者姓名、电话、主诉或治疗细节。

- 没有占用且未开始：可以选择“调整未来空闲时段”或“停用原时段”。
- 有预约/接诊或未到期邀约：说明为什么不能变更，提供“查看本店预约运营”和“查看本店候补”。前台另行与患者协调；主管不因此得到患者改约权限。
- 过期但未回收邀约不再保留机会；本功能不自动回收其状态。等待中的候补或未发布草案不保留特定出诊。
- 已开始、历史、已停用或关联异常：不直接变更；不提供历史恢复或删除。

**调整：** 填写新的开始/结束和固定依据→预览新旧时间（尚未保存）→明确确认→原记录停用并保留历史，另建同诊所同牙医的新时段。旧记录提供替代记录入口，新记录提供原记录入口。

**停用：** 预览原安排和影响→明确确认→只改变原记录有效标志，不新建记录、不删除历史。

## 3. 变更保护

1. 当前主管身份、授权诊所、对象和工作上下文分别核验；本轮不借用账号的其他角色。
2. 编辑和预览各有不同类型的签名令牌，确认有效期15分钟。签名不是加密，不是授权凭据，不要公开分享。
3. 关联记录和审计游标参与快照。预览后出现新预约、邀约或其他变更，即使后来又撤回，旧确认仍须重核。
4. 最终提交锁定当前账号、上下文、角色授权及源出诊，重新检查。相关预约/邀约服务使用相同源出诊行锁。
5. 新替代时段受既有PostgreSQL同牙医有效时段排他约束保护，包含跨店重叠。仅改当前店范围，不能将牙医或诊所夹带改掉。
6. 原记录停用、新记录创建和审计一起提交。失败不留下只停旧记录的中间状态；不直接更新Visit/WaitRequest/WaitOffer/Invoice。
7. 同一次成功确认在当前授权/上下文/期限仍有效时返回既有结果。后续合法变更不被重放操作撤销。
8. 不确定回执时先查询原记录与维护记录，不能直接判定未保存或自动再建。

上述是已编码的合同。事务、HTTP及竞争仍须用真实PostgreSQL验证；不能只凭函数上有atomic或截图认定成立。

## 5. Windows：先独立验证，不立即覆盖v0.7

完整源码包解压至新目录，不复制旧.env、私密账号文件或旧数据卷。Docker Desktop本地Linux引擎就绪后，在新目录CMD执行：

```cmd
VERIFY_ISOLATED_WINDOWS.cmd
```

入口不依赖Windows宿主机Python，使用独立Compose项目和临时PostgreSQL。预期门槛是本轮基础检查、Django check、迁移差异、临时库迁移和全部Django/PostgreSQL测试。

实际框架发现数量以真实日志为准，不能将本文件中的测试定义数量当作已经执行。

检查本次`evidence/verification/gate-*.json`中每个步骤和`all_gates_passed`；同时核对清理返回码为0。失败时保存首个错误与末尾摘要。不要发送.env、密码、API Key、真实患者资料或数据库归档。

绿灯后保存原源码与数据库私密备份，在带数据副本验证升级和人工主流程；之后才使用累计包。`--after-isolated-pass`只是显式操作确认，不是测试通过证明。不得删除旧卷或改用SQLite绕过失败。

## 6. 少量关键人工验收（在新副本中）

|场景|应核对的实际事实|
|---|---|
|空闲时段只到预览|数据库和审计没有新增；页面明确尚未保存|
|确认替换|旧ID和旧时间保留但停用；出现新ID，牙医诊所相同|
|有关联预约|维护被拒绝，不取消、不搬移患者；主管只能看协调范围|
|有有效邀约|维护被拒绝；到期后重新读取可按规则处理|
|预览后另一个前台预约|旧确认被拒绝，预约与原出诊仍一致|
|两个主管同改原时段|最多一次成功；只有一个替代结果|
|旧草案在停用后发布|发布失败，不把草案自动迁往新时段|
|切店、切身份、直访其他店URL|拒绝；不能借同账号另一角色的权限|
|重复已成功确认|不新增另一时段或重复维护事件|

## 7. 明确没有完成的范围

本轮不是完整排班管理：不能调整已开始/带占用的时段，不换牙医或诊所、不扩展为多人接诊，不自动改约或通知患者，不实现协调工单、暂停接收新约但保留旧约的复杂状态模型，不认证医学资格，不上线、不做Mac迁移。R4.4不重新生成；规约作为增量材料归档。

后续优先级：取得真实框架/数据库结果并修复问题→在有数据副本上跑完整业务链→明确前台协调任务与影响处理→再考虑复杂出诊资源及可靠通知。
