# ADC 物理设计 v0.3

**性质：工程实现候选；所有 ORM/SQL 尚未在目标引擎执行。**

逻辑链：事实粒度 → 字段类型 → 同表约束 → 跨表一致性 → 命令与事务 → 验证证据。

## 1. 与材料的关系

CASE 第1–2页给出患者、过敏、牙医、诊所、资格、治疗、季度成本与一就诊一结算单的信息需求。NOTE3 第1页区分需求与设计，第11页讨论模型、不变量及操作前后条件；NOTE4 第7页要求功能与数据并行细化，第11页强调清楚的模块联系。

这些材料**没有**指定 Django、数据库字段长度、锁算法、数据库触发器或下面的模块名；这些均为本项目设计 [D]。v0.2 具体逻辑对象可对照 `reference/schema_model_v0.2.json`；本轮没有把患者身份改成患者网站账号。

## 3. 统一类型决策 [D]

| 事实 | 源码选择 | 设计理由与范围 |
|---|---|---|
| 内部主键 | BigAutoField | 不把内部ID当授权凭证；业务编号另存 |
| 患者/就诊/账单编号 | varchar(40)，UUID4派生字符串，唯一约束 | 非固定演示流水号，不用“查最大号+1”生成 |
| 业务时间 | DateTimeField + USE_TZ=True | PostgreSQL目标为 timestamptz；页面按Asia/Shanghai解释和显示 |
| 出生日期 | DateField | 不把生日当瞬时时间，也不保存不断过时的“年龄” |
| 电话 | varchar(32) | 保留前导零、区号和标点；不设唯一 |
| 治疗数量 | DecimalField(12,3) | 单位含义另存，不能使用浮点金额 |
| 标准/实际单价 | DecimalField(12,2) | 非负；零价格需要原因与未来业务授权 |
| 行金额/版本总额/成本 | DecimalField(16,2) | 先对每行按HALF_UP舍入，再求和 |
| 未录入成本 | NULL + MISSING状态 | 与“已确认零成本”不同 |
| 当前业务关系 | 外键/连接表 | 过敏、资格等不塞成逗号分隔的字符串 |
| 历史展示快照 | JSONField | 仅用于固定历史内容；目前DB只限制对象类型，完整schema和复核服务待实现 |

字段上限是工作方案，不是根据真实门诊量测得。金额字段溢出必须报错，不能静默截断。全字段清单见 `FIELD_CATALOG.md`。

## 4. 约束分层

| 规则 | 本轮源码载体 | 不能据此声称什么 |
|---|---|---|
| 唯一编号、一个Visit一张Invoice | 字段 unique / OneToOne | 未执行并发插入，不可声称已经验证唯一性 |
| 同患者过敏项不重复、同牙医资格不重复 | UniqueConstraint | 不代表过敏/资格已经过真实专业验证 |
| 状态、到诊标志、时间、取消元数据一致 | CheckConstraint | 普通状态命令是否被授权仍由服务判断 |
| 牙医/患者预约区间不重叠 | 两个ExclusionConstraint；[start,end) | 不解决通勤、椅位、设备、实际治疗超时 |
| 同牙医有效出诊安排不重叠 | AvailabilitySlot的ExclusionConstraint | 不等于优化排班 |
| 每次一个DRAFT、一个OPEN更正 | 条件唯一约束 | 不意味着更正流程已实现 |
| 角色范围含NULL时去重 | 分别对clinic非空、空值建立条件唯一约束 | 不能依赖普通多列UNIQUE自动去掉所有NULL重复 |
| Invoice版本必须属于同Visit | 复合外键(id,visit_id)引用 + SQL保护 | 两个独立外键不能证明业务归属相同 |
| 已发布版本/治疗行、审计不可普通改写 | PostgreSQL BEFORE触发器候选 | 不防数据库所有者、禁用触发器、TRUNCATE等特权操作 |
| 已闭合必须有单；当前金额/结果一致 | DEFERRABLE约束触发器候选，在事务结束检查 | 不是全部基线不变量的形式化证明 |
| 过敏状态与关联项、出生日期、范围授权 | 受控服务 + 待执行测试 | 不能说普通数据库CHECK已经覆盖跨行与动态时间规则 |

模型中46个显式命名约束包含检查、唯一和排斥约束；SQL保护迁移还增加额外约束/触发器。该计数不包含字段自带的所有主键、外键、唯一性或正数检查，因此不当作最终数据库约束总数。

## 5. 写入流程与失败边界

页面和表单只收集、展示输入，不直接保存关键状态；服务重新读取权限与记录。`create_appointment`、`change_appointment`、`reschedule` 等把业务数据与成功审计放在同一 `transaction.atomic()` 中。

预约中的牙医和诊所从已锁定的出诊时段取得，不相信浏览器独立提交的牙医/诊所组合。没有用 MAX(id)+1 生成业务号。后端按已登记约束名识别资源冲突；不把任意数据库异常误报为“有人抢了时段”。

锁顺序工作协议：写入账号 → 相关角色绑定 → 出诊时段按主键升序 → 目标Visit。新增角色的技术命令对涉及账号按主键升序锁定。普通角色变更必须使用统一边界，直接数据库所有者修改不在应用层保证内。

跨店改期同时验证原店与目标店授权；先在同一事务中将旧预约标记为被替代，再尝试建立新预约，复制的是治疗意向，不是已经执行的治疗。新预约失败会回滚旧状态更新；用 `lock_version` 拒绝陈旧命令。并发数据库保护仍需以两个独立连接验证。

没有在v0.3实现“完成并开单”的服务。下一版应统一采用 Visit → VisitRecordVersion → TreatmentRecord → Invoice 的锁与写入协议，不能仅通过新增按钮直接操作模型。

## 6. 本轮特别记录的细化决策

**D31：患者增加 created_in_clinic。** 用于授权前台在第一次预约创建之前查看自己刚建立的档案；它是建档来源，不是永久所属诊所。患者仍可跨店预约，权限也可以来自已有Visit关系。

**D32：本轮是本地候选，不开放生产配置。** 这是阶段门槛，不撤销最终公网目标。安全节流、生产服务、TLS、完整依赖锁定和备份恢复需要独立完成。

**D33：有历史引用的出诊时段身份/时间在v0.3不原地调整。** 本轮只有新增时段入口；对已有记录的安全编辑能力留到下一增量，不能将当前限制宣传为已实现完整排班维护。

**D34：改期后继在物理层要求由后来创建的自增ID记录引用较早ID。** 该限制服务于新建后继的既定命令，辅助阻止环；业务发生时间仍由日期字段表达，不能从ID推断真实就诊时间。

**D35：过敏三态具体化。** KNOWN要求至少一项；NO_KNOWN和UNKNOWN都不得同时带有效项目。有已经明确记录的过敏项时应进入KNOWN，KNOWN不保证已经发现所有过敏。应用不作临床安全判断。

## 7. 尚未落实的完整性规则

未开放care业务前仍须补齐并验证：完整快照schema、同就诊的前后版本链、更正请求与新发布版本的一致性、申请人/审核人/负责牙医权限、确认资格和价格变更授权、首次发布与更正发布区分、开单幂等、当前版本切换的并发保护。当前DB护栏不等于以上规则全部实现。

财务方面仍须完成清单确认失效、含零收入牙医、成本完整性、当前版本收入汇总、查询时刻/口径记录、缺失和亏损政策提示等服务。单有Quarter/Cost表不足以宣称已经实现绩效管理。

当前没有完整患者基本信息编辑、停用/删除工作流、角色撤销网页、真实病历管理、收款、退款、税务能力。不要通过通用管理后台绕过未完成服务。
