# 课程报告工程章节草稿：从逻辑模型到候选实现

本章节是阶段性材料，不可直接写成“系统已成功上线”。

## 1. 设计依据与追踪

本项目以牙科连锁案例的信息需求为业务依据，以课程note中的需求—设计—代码追踪、模型不变量和逐步细化思想组织工程过程。在v0.2逻辑模型基础上，本轮将20个逻辑对象映射为Django模型，并编写物理约束和迁移候选。具体字段长度、技术框架与权限实现均为本项目设计，不来自案例明文规定。

## 2. 模块与业务边界

系统采用模块化单体。账号授权、基础目录、患者、预约、接诊结算与季度成本分模块保存。当前已编写的首个业务子集为建档—预约—到诊，并包括取消、爽约核实和保留历史的改期。接诊内容、账单版本和季度成本的表结构已提出，但相应业务流程尚未全部实现。

关键业务写入通过服务统一检查角色、诊所范围、当前状态和时间条件。技术管理员不借助框架超级用户标志默认获得患者/财务界面权限，患者业务编号也不产生患者登录账号。

## 3. 一致性设计

针对重叠预约，分别按牙医与患者使用时间区间排斥约束；仅比较开始时间不足以表达冲突。改期采用前后记录关联，事务中任一步失败应回滚旧预约状态。针对结算历史，逻辑单据与治疗内容版本分开，当前单据引用同次就诊的已发布版本，历史发布内容不原地覆盖。

同表属性采用显式检查约束；跨表关系和事务最终状态采用复合外键及必要的PostgreSQL触发器候选。对于未录入成本，保存NULL和状态而非自动填零。框架事务、唯一性、幂等性与业务正确性是不同的验证对象，不能因为使用了数据库便认为所有规则已得到证明。

## 4. 验证现状

生成环境未安装Django、PostgreSQL和Docker，且依赖获取失败。因此本阶段没有实际执行数据库迁移和业务网页测试。已经执行46项框架无关规则测试和11项静态检查，合计57项通过；另外编写了28项集成测试和2项独立连接并发测试，但尚无运行结果。

这些结果只支持规则函数在被测输入上的表现及部分源码结构一致性，不支持“系统全部功能正确”“数据库并发已验证”“网站可以正常运行”等结论。后续需要保留真实命令、运行环境、输出与截图，再更新本节。

## 5. 下一阶段

先在独立本地PostgreSQL环境通过系统检查、迁移一致性检查、实际迁移和集成测试，然后进行浏览器操作验收，再实现治疗确认、首次开单、零治疗关闭与账单更正。公网发布在HTTPS、登录节流、最小权限和备份恢复等门槛之后进行。
