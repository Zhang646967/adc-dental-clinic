# 增量验收：待在Django/PostgreSQL和真实浏览器执行

1. patient_demo_a/doctor_a单身份登录直接到对应工作台；multi_demo仍显示身份选择。单主管直接到主管主页，但诊所仍由用户在工作台选择。
2. 主管有两家店只有一个角色，不应被算成两种身份；停用授权店或撤回授权后旧页面不能继续写。
3. 候补表单开始为空时结束不可选；选未来日期和时刻后结束只提供至少晚30分钟且在14天内的值；把开始移到已选结束之后，旧结束必须清空并解释。
4. 在美国/中国浏览器时区都使用服务器北京时间；关闭JavaScript或手工构造非法请求时后端拒绝。不得读取用户精确位置来确定业务日期。
5. 主管从候补列表可到排程页；打开入口不创建方案；患者/前台不出现主管发布按钮。期限来自实际已发布邀约。
6. 已接受邀约有“查看正式预约”，不被误导为仍需确认；原预约编号和历史金额不改变。
7. tech_demo进入账号与授权，创建一个自定密码的普通演示账号；创建后无业务角色，再显式授予某诊所主管。由新账号登录验证身份与范围。
8. 管理操作输入错误技术密码、过期目标签名、其他人的grant_id、旧工作上下文时均不改变数据。患者/牙医直接访问技术URL被拒绝。
9. 有未完成预约/候补的目标不能停用；未关联任务的普通目标可停用再显式启用，资料不删除。技术页不能修改自身或SYSADMIN目标。
10. 登录用户可用旧密码修改自己的密码，成功后重新登录；技术重置目标密码后旧密码不可用、旧会话失效。不要将密码发到聊天或报告。
11. 记录治疗指南到核对明细为止；完成接诊/开单为另一独立指南；任何指南“下一步”不提交表单。
12. 最后重跑原候补接受、重复确认、跨店上下文、接诊结算与季度统计；形成版本化验收日志。
