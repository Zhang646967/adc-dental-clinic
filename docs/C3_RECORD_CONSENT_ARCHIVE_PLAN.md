## 2. 规范依据与默认边界

- 电子病历应有身份、操作痕迹和归档管理；归档后确需修改须履行医务批准并保留痕迹。系统据此设计准确版本和追加补正。[电子病历应用管理规范，第9、14—18条](https://www.beijing.gov.cn/zhengce/zhengcefagui/201905/t20190522_59868.html)
- 机构保管的门急诊电子病历，保存期限以患者最后一次就诊时间为基准且不少于15年；首轮按诊所保管主体配置，不提供到期自动销毁。[同规范，第19条](https://www.beijing.gov.cn/zhengce/zhengcefagui/201905/t20190522_59868.html)
- 书面知情同意应识别适格签署人；不同情形的代理不能仅由手机号、亲属称谓或预约授权推定。[病历书写基本规范，第10条](https://www.nhc.gov.cn/wjw/gfxwj/201002/79d42b9c8b3f47ee91000d31de116784.shtml)
- 信息使用应按职责、任务和时限授权并可追溯。以下新增临床复核、复制职责须独立授予。[2025年电子病历信息使用管理通知](https://www.nhc.gov.cn/yzygj/c100068/202506/c68abee7c54b4651a774cd533761780b.shtml)
- 可靠电子签名有专属控制、改动可发现等要求；微信登录、勾选、手写图像或文件摘要不自动满足这些要求。第三方认证是可选实施路径，不将“购买CA”设为所有课程流程的前提。[电子签名法，第13—16条](https://www.beijing.gov.cn/zhengce/zhengcefagui/202202/t20220208_2606143.html)

本轮先提供课程电子确认及纸质原件登记路径，明确记录证据类型；签署适配接口保留可靠电子签名路径。非合成临床环境不得将课程确认当作可靠电子签名。真实机构启用前，由其医务负责人确认模板、签署证据、权限和保管制度的适用性。

不扩展住院、急救自动豁免、处方／发药、完整PACS、大型DICOM或全院总账。C4处方与C5耗材继续排在C3之后。没有实际专业审核、电子签名服务或手机验收时，相应结果保留未完成。

## 3. 病历文书：一次接诊形成完整证据

### 3.1 正常办理

1. 医师从已到诊患者进入接诊，复核本人、诊所、医师、服务及自述来源；过敏未知仍保留未知，不自动填写“无”。
2. 按初诊／复诊整理主诉、病史、检查与牙位牙面、辅助检查来源、诊断／判断、治疗计划；已有数据引用具体版本，由医师复核，不整段自动照搬上次结论。
3. 有实际处置时，引用已有实际执行记录；无治疗也形成检查、判断及医嘱记录。补齐离诊注意事项、复诊要求和沟通内容。
4. 预览完整文书，显示来源版本、医师及诊所信息、实际发生／录入／确认时间。医师核对后确认准确版本；需要纸签或可靠电子签名时关联对应证据。
5. 常规文书由作者确认。实习／试用记录和诊所指定的重点病例进入相应上级复核；一般病例采用缺项提醒与抽查，不一律增设第二名医师审批。

本轮不把现有“确认检查”按钮直接重命名成法定签章。检查通常在治疗前确认；最终文书还要包含之后的处置和医嘱。具体字段扩展优先复用现有记录，新增文书层引用准确来源，避免复制出另一套可独立修改的病历。

### 3.2 状态与更正

文书版本：`草稿 → 待确认 → 已确认／具有指定签署证据`。待复核、需补正、对外发布状态分别呈现，不混成一个“已完成”。

- 未确认草稿可以修改或明确弃用；保留操作依据和历史。
- 已确认内容不覆盖。更正创建新版本，说明原因、变化和关联原版本，重新确认；原版本仍按权限可追溯。
- 已归档后的更正由不同于申请者、且具有专项医务职责的人员批准，再形成补正版本和新病案包；切换角色不能自审，没有“撤回归档后直接改原文”的捷径。
- 迟记保留实际发生、录入及确认时间，并记录迟记理由；签署时间取实际确认时间，不能倒签。
- 确认与签署使用经核验的服务端时间源，并衔接已有时钟监测；客户端显示时间不能改写服务端证据时间。
- 发现错患者／误归属时，登记争议、限制错误内容继续对外发布并转医务处置；不自动迁移到另一患者或删除原证据。

### 3.3 实用衔接

**接诊结束、文书完成、账单结算、病案归档是四条相关状态。** 新文书任务不额外占用椅位；沿用已有临床最小事实及接诊完成规则释放资源。待签、待补正或待质控形成有责任人和期限的工作台任务，不标成已归档，也不让前台等待归档才能按原规则结算。

更正文书不自动改收费项目、医保、已发布账单、收款或退款。发现费用问题时，关联原财务流程和独立复核。已发生治疗的真实事实不能因为材料不足而被隐藏。

思维导图：病历 → {初诊／复诊、来源复核、牙位检查、诊断、实际处置、离诊医嘱} → {作者确认、必要复核} → {更正留痕、超期任务}；椅位与资金沿原流程办理。

## 4. 知情同意：具体行为、具体版本、适格签署人

### 4.1 告知与办理

1. 由临床规则目录判断实际治疗项目的告知要求；预约服务名称和收费项目名称不能单独代替临床判断。普通检查不统一增加复杂签字；规则未知时交医师核对，不默认“无需”。
2. 由具备职责的临床人员审核版本化模板；门店主管发布宣传资料的权限不包含审核医疗风险内容。
3. 医师据实际诊断及方案，说明治疗范围、牙位、必要性、主要风险、替代方案、相关麻醉／材料安排、费用说明及术后注意事项，并记录患者疑问与答复。
4. 患者可同意、拒绝、暂缓或要求进一步说明。保留医师告知和患者决定的准确内容及版本；“已读”不等于“已同意”。
5. 签署人分本人、经核验的法定代理／监护人及适用情形下的医疗授权代理。独立核验依据、范围和有效时间；现有预约代办授权不能直接用于医疗同意，微信身份也不自动证明法定代理关系或同意能力。
6. 网站／患者小程序只提供其本人或该份文书专门授权范围内的展示与决定；现场纸签由医师核对并登记原件及采集件。纸件登记人／见证人不是患者签署人。

同意内容冻结：患者和诊所、实际项目／步骤、牙位、关键风险、适用阶段、模板版本、告知医师、签署人及依据、决定、实际时间、证据类型和文书摘要。

### 4.2 状态与适用性

办理：`拟定 → 已告知／待决定 → 同意／拒绝／暂缓`。同意事实保留；其未来适用性另记`有效／已替换／已撤回／已过期／待重新核对`，不改写过去。

- 治疗范围、牙位、麻醉或其他重要内容变化时，重新告知并形成新版本；旧同意不能替新内容签字。
- 分次治疗明示覆盖的阶段及有效条件，每次开治核对；未变化的既定范围不机械重复签署。
- 改期本身不一律使同意作废；超出期限、指定医师或临床条件变化时重新核对。跨店不自动共享同意或病历权限。
- 拒绝／暂缓不自动取消预约、不自动退款；医生讨论替代安排，前台按原授权办理改期或取消。
- 撤回限制后续未实施部分；已完成治疗和原同意事实保留。进行中情形由医师处置，不由系统自动中断、回滚治疗或资金。

### 4.3 必须补的治疗前核对

现有`confirm_execution()`登记的是已经发生的实际执行，只有在这个入口检查同意，不能声称实现“治疗前控制”。C3.2因此增加明确的开治核对：就诊人、实际项目／牙位、医师原有专业授权、同意版本与适用性相符后，保存核对结果；实际执行引用该结果并重检。患者签字不会授予医师本来没有的技术权限。

如实际治疗已经发生而缺少事前材料，必须能够诚实补记、标明缺口、派发医务复核；不伪造事前核对、不倒签，不阻止记录真实发生的医疗事实。正常拟开始的必需同意项目，在缺同意时暂停新开治；系统也不宣称能物理阻止线下行为。

思维导图：实际治疗 → 风险规则 → {告知、问答、签署资格} → 准确版本决定 → 开治核对 → {继续、重签、拒绝／撤回、缺失处置}。

## 5. 归档与复制：冻结准确证据，保留继续诊疗能力

### 5.1 归档办理

生成清单 → 核对必需文书／确认／同意／附件 → 必要质控 → 冻结病案包 → 归档回执。

- 冻结的是每份文书、来源记录、签署证明、模板及附件的具体版本；保留文件摘要、生成时间、保管主体及清单。后续姓名显示、模板、门店介绍变化不重绘旧文书。
- 原始签署文件原样保留；预览或压缩件另标识，不转换后假称原件。首批限定小型PDF、JPEG、PNG，采用统一证据存储接口，优先沿用数据库二进制及现有加密备份；大型影像和对象存储迁移另立增量。
- 有缺项、待处理更正或必要复核未完成时进入待补正，显示负责人和期限；生成／归档失败明确重试，不显示假成功。文书生成与通知处理分开，避免大任务阻塞通知心跳。
- 归档时限按经审核的机构制度配置；首批提供当次未完成与次工作日待办提醒，不将“24小时”统一写成所有门诊的法定归档期限。
- 归档不关闭后续复诊。后续新就诊、新报告或补正产生新的关联版本／病案包，不能改旧包。

状态：`待整理 → 待核对 → 可归档 → 已归档`；缺项返回待补正，生成失败返回待重试。已归档包没有回到可编辑草稿的状态。

### 5.2 复制、调阅及封存

- 申请 → 核验申请人身份／依据／目的／范围 → 授权审批 → 生成准确版本副本 → 交付及领取记录。可独立读取的PDF附版本清单；纸质副本的机构核验／盖章另留办理记录，不绘制假印章。
- 患者在线查看限已发布且本人有权访问的内容；临床代理仅按专门授权范围。账号停用不一概否定线下依法申请复制的途径。
- 前台普通排班／接待权限看办理状态与联系待办；病案办理职责须显式授予，办件人员只接触已批准范围。医务复核权限、前台病案办理权限、技术维护权限互不代替。
- 保存期限按保管机构与患者最后就诊时间计算；本阶段无自动删除。争议保全与依法封存分开：系统先保护准确副本、记录原件／介质位置、参与方及办理依据，不将一个“封存”按钮当作已完成法定共同签封。原病历可按规定继续记录，新部分另保留。[电子病历规范，第21—25条](https://www.beijing.gov.cn/zhengce/zhengcefagui/201905/t20190522_59868.html)
- 病历长期保管与服务器7份／异地30份备份轮换是不同制度；短期课程服务器不能证明长期保管能力。正式保管需承接机构、存储与迁移安排，备份轮换不能触发病历原件销毁。

思维导图：病案包 → {准确文书、签署、附件、清单} → {归档、批准补正、新版包} → {调阅、受控副本、争议保全} → 长期保管与恢复。

## 6. 岗位、模块与数据设计

| 岗位 | 主要职责及范围 |
|---|---|
| 接诊医师 | 获授权病例的记录、解释、作者确认、开治核对及有依据补正 |
| 经机构任命的上级／质控／医务审批人员 | 指定病例的复核、必要审批；单独配置职责、依据及期限，不由现有资质审核任命自动推定 |
| 患者／经核验医疗代理人 | 本人或指定文书范围的决定、撤回及副本申请；普通代约人无此默认权限 |
| 前台 | 保留排班职责，办理联络与文书待办进度；额外病案办理职责只适用批准办件 |
| 主管／总部 | 本店／全链完成率、超期和问题汇总；不因此获得病历正文读取权 |
| 财务 | 沿原账单与收退款流程核对；不改临床正文、不给患者代签 |
| 技术人员 | 配置、备份、恢复及职责治理，不代替医务审批或自动获得正文浏览权 |

先在现有七角色基础上设计目的明确的专项职责，不为每个按钮增加角色。实习人员代理录入与上级确认仅在其人员类别及授权契约建立后启用，不把现有医生默认标为实习或上级。

模块保持Django＋PostgreSQL模块化单体：临床模块拥有事实；文书模块拥有来源快照、确认及补正；同意模块拥有模板、签署资格、决定与适用性；病案模块拥有清单、归档、保全及复制；财务仍拥有金额和复核。

模块通过`prepare/confirm document`、`check consent applicability`、`record start check`、`create archive package`、`request/release copy`等定义明确的操作协作，不跨模块直接改行。沿用当前上下文、授权重检、锁序、服务器预览、版本游标和操作ID；网络重试返回已保存结果，不重复签署、归档或开单。临床正文和证件值不进入运行日志。

| 医疗同意 | 患者／独立医疗代理依据 → 告知版本／治疗范围 → 决定／证据 → 开治核对 |

复用既有身份和临床源表；现有共享查阅同意只用于原转诊用途，方案决定只表示选择。实施时保留全部64份旧迁移，新增迁移；旧记录标明历史确认方式／未提供新签署证据，不补造签署、同意或归档。实际表数、ER、字段与触发器清单在PostgreSQL迁移后生成核对，规划图不覆盖实际ER。

## 7. 开发顺序与完成门槛

| 批次 | 本轮可交付结果 | 完成门槛 |
|---|---|---|
| C3.1 病历文书闭环 | 初复诊完整文书、来源快照、作者确认、签署证据类型、未归档追加更正、待签／迟记待办 | 医师从接诊完成可读文书；新版本不覆盖旧文；原资源和资金事实保持正确 |

| C3.3 归档与受控副本 | 清单、准确文件、质控／医务审批、归档后补正、复制交付和争议保全记录 | 准确包可独立读取，审批边界明确，后续记录不重写旧包，不能用普通登录获取公开下载 |
| C3.4 综合验收与交付 | 跨模块场景、七角色／多诊所、容量、恢复、报告及保护更新 | 完整回归、准确提交CI、20店混合负载、新文书证据加密恢复及原数据对比通过 |

**下一轮从C3.1开始**；先确认字段、病例范围、证据模式及作者／复核职责，再追加模型和表单。不一次引入微服务、区块链、复杂审批引擎或全量影像平台。

C3.1首轮实现清单：复用现有接诊及版本来源；补齐诊断／判断、实际处置摘要、离诊医嘱与复诊安排的完整文书投影；增加文书草稿／准确版本、作者确认和证据类型；提供预览、历史对比、未归档追加更正、待签／迟记任务及可打印展示。先完成A01—A08、A19—A21对应业务，再进入医疗同意；归档包和可靠电子签名服务不提前标为完成。

Codex负责系统业务、权限、数据库、文书生成、网站以及必要患者客户端业务代码；WorkBuddy继续只负责小程序工程配置、编译、预览、域名／体验成员和真机部署验收，不另建病历库或在客户端重写规则。服务器未购买不阻断本地开发；真实签名、手机、固定HTTPS及专业审定分别记录。

## 9. 报告、启用与交付

规划只更新路线和规约，不重启现系统、不修改当前临床数据、权限或64份迁移，不把计划用例标成实现。实施后按实际表结构补充病历文书、医疗同意与归档复制三组ER视图；领域图、状态图、规约及测试追踪同时更新。

课程报告沿用原Word／PDF文件名；正文讲业务职责、过程、状态、关系及验收，部署与工具说明另放指南。每批准确提交CI通过后，加密备份并保护更新；旧账号、私有配置、RC标签和历史保留。旧病历可读且明确原确认方式；新规则按诊所制定启用时点和在办事项安排，不自动补造历史签署。
