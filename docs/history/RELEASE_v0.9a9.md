# v0.9.0-alpha.9：有责任的出诊协调任务

父版本alpha.8；Mac迁移继续暂停；报告R4.4保持冻结。最后确认运行实例仍是Windows v0.7。本轮没有连接用户实例。用户已要求到v1.0候选完成再集中部署和验收，不要求本轮运行任何命令。

## 本轮业务结果

主管对已经明确暂停新增的未来有效出诊发起任务（停用目标或调整目标）；本店前台自行受理、按原业务流程处理、记录有限的办理声明，在实际关联已无阻断时提交主管复核；另一账号主管再次核对后结束任务。主管另行办理原出诊维护，不因工单通过就自动停用/调整。

任务状态：OPEN待受理 → IN_PROGRESS协调中 → READY待主管复核 → CLOSED协调核对通过。受理人可以退回队列；主管可以退回重新受理或撤销未结束任务。撤销任务不恢复接收、不撤销患者承诺。已结束任务不删除或重新打开；新计划另建任务。

## 操作路径

- 主管：本店出诊详情 → 明确暂停新增 → 发起协调任务 → 核对目标与依据 → 预览 → 确认。已有未结束任务时查询原任务。
- 前台：本店协调任务 → 受理 → 进入原出诊协调 → 原预约/邀约流程 → 回到任务记录声明 → 重新查询后提交复核。
- 主管：协调任务 → 核对当前聚合事实 → 复核通过/退回 → 回原出诊完成独立维护。
- 新任务页面不直接改变患者业务。原预约与邀约的写命令保持父版字节，不建立第二套取消/改约实现。

## 边界与保护

1. 同一出诊同时最多一条OPEN/IN_PROGRESS/READY任务。所有任务操作先核验当前身份、诊所和对象，不能借账号另有身份放行。
2. 前台只可自行受理；只有当前受理人能够记录、退回或提交。主管可将未结束任务退回队列，解决受理人停用/撤权/无法工作后的交接，但不直接替另一人受理。
3. 声明类别只有尝试联络、等待决定、转原流程办理、请求协助等固定选项。前三类必须指向本出诊的明确预约/邀约。声明不证明已联络、已同意或已保存，不清除任何阻断。无姓名/电话/病史自由文本。
4. 提交和批准必须重新检查完整有界关联，原出诊仍未来、有效、已暂停，且无受保护预约/接诊、有效邀约、异常或超上限。已到期但未回收邀约不再占位；已接受邀约按其对应预约检查。
5. 主管批准还核对前台提交时的事实摘要。提交后暂停/恢复、关联变更等均需退回重新核对；时间边界实时重验。同一账号不能切换身份自审本次提交。
6. 有效旧邀约仍可兑现原承诺，不能为了结案而批量拒绝、取消接诊或伪报爽约。若原场次已有受保护临床记录，本普通流程可能无法结案，应转独立受控处置。
7. 预览/确认分两次，不在GET中写业务。15分钟签名绑定账号、角色、上下文、源出诊、任务/业务摘要和操作编号；签名不是加密。源变更或任务A→B→A不能使旧确认复活。
8. 同次成功请求在当前权限/期限内重放只返回既有任务和当前状态，不逆转后来合法状态。读失败或回执不确定先查询，不自动重发。
9. 任务与审计同事务。写入顺序为账号→上下文→当前授权→源出诊→任务。原预约/邀约及出诊维护继续使用源出诊锁协议。它不是对任意DB owner SQL的全域保证。
10. 主管任务详情只展示聚合影响和工作人员责任记录，不展示办理声明的患者相关对象编号；前台可看到声明指向的预约/邀约编号。原详情独立授权。不存在“有任务就有患者访问权”。

## 模式与部署

新增`coordination.0002_coordination_tasks`，创建CoordinationTask表、部分唯一约束、状态/责任/复核约束与身份/历史更新保护触发器；原14份迁移字节不变。使用任务后反向删表会拒绝，须按停写和备份恢复流程评估。新代码须完成迁移后才能访问新页面；旧代码不理解这些任务记录，不能混用来处理任务。
