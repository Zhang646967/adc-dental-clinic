# R2.4.3 重现与独立核对

固定源码与隔离实例 → 准备合法数据 → 三十分钟真实调度 → 有界附加业务 → 原行和资金核对。

## 环境与数据

采用 acceptance.json 中的准确应用提交。全新本地 Docker 项目、独立数据库卷和 loopback 端口，不向原 Mac 的18000/18020端口运行。按原 RC 工具生成私有配置，保留独立owner/runtime数据库账号；只有新合成实例显式设置 `ADC_CAPACITY_REHEARSAL`，关闭外部AI。五个运行服务的CPU/内存上限见 acceptance.json，业务四服务沿用R1，observer另行列出。

用 [multiclinic_seed.py](../../scripts/multiclinic_seed.py) 的 `--synthetic-empty-only` 准备五诊所、20个测量账号、10004名患者、10505条Visit、500张100元账单、150件设备及500笔独立审核收款。私有actor文件由种子生成，不放入公开仓库。

用原浏览器流程在每店完成20.02元退款、两笔10.01元分次收款、10.01元设备支出及等额冲回，分别由不同财务账号审核；每店接受6行外部流水并核对5笔，首店再追加独立审核的凭据更正。独立核算四类金额和24有效/1需重核匹配。UX2浏览器另完成两例100元实际治疗；未被发布的反例输入不计为业务效果。保留五名医生的专用CHECKED_IN负载对象。

负载前后按原主键范围记录所有原始持久行的计数和排序内容摘要；二进制流水用字节摘要及长度编码。排除瞬时Session、WorkspaceContext、User.last_login，并单独核对五份允许修改的草稿。新增对象不能使原有行消失在核对范围之外。

## 实际测量

[原负载驱动](../../scripts/multiclinic_load.py) 保留二十个真实HTTP会话，签名表单和服务器版本。以新建实例的真实root/project/port参数运行：

```sh
python scripts/multiclinic_load.py \
  --root /absolute/synthetic-rehearsal \
  --project adc_rc1_INSTANCE \
  --port 18074 \
  --name capacity-30m \
  --seconds 1800 --rps 5 --arrival-mode waves
```

每四秒同时提供20个请求，共450批；其中每批4个写请求，在5名前台和5名医生间轮换。9000次中7200读、900建档、900草稿保存。测量从调度的到达时间计算延迟，包含客户端排队；不重试。记录真实墙钟、单调时间、最大提供间隔和最大in-flight；二十线程存在不等于实测并发20。

该命令拒绝未标记实例、原演示端口、远程Docker和不符的actor角色构成。测试期间使用仅随进程存活的防空闲睡眠措施，未安装定时任务；若实际睡眠造成时间缺口，continuity gate仍判失败。

每约10—12秒采集五服务资源，约30—36秒独立读取运行状态；observer自身采样/过期配置维持30/90秒。检查运行源码身份、容器OOM与重启、数据库死锁计数及统计epoch。没有将数据库查询失败写成零积压。

第1分钟开始，五店主管各导入一份1000行CSV（1条合法100元收款匹配建议、999条可见的0.01元未匹配支出），经另一财务账号分别确认；每次签名确认也并发提交相同内容以检验同结果。五店协调任务在第2/6/10/14/18分钟依次正常提交，产生真实outbox/inbox。附加财务HTTP、采样和通知操作独立计量，不混入9000分母，也不等同于所有商业写入的负载代表性。

## 独立核对

- HTTP全部9000次完成、读写分母正确，零丢弃/意外失败，p95≤5秒；峰值in-flight为20，墙钟和单调时间相差≤2秒，提供间隔≤5秒。
- 按返回主键和运行标记核对900个不同患者与正确诊所；五份草稿各增加180版，最后内容等于最后一次成功保存，仍CHECKED_IN且未发布；数据库有1800条对应写审计，业务写入最大间隔≤5秒。
- 所有负载前原有持久行摘要一致（五份草稿另核对）；账单与全部POSTED资金不被导入、匹配或负载改写。额外审计应等于1800次测量写入、20次导入/匹配和5×3次明确协调动作，共1835条。
- 原始CSV字节摘要与保存摘要、版本和行数一致；累计5030行、29个有效匹配、1个需重核历史决定。没有相同渠道/交易号重复行、同资金重复活动匹配或同事件/授权重复消息。
- 五条通知各只尝试一次、消息数等于原收件授权数（五店分别2、2、1、1、1条，共7条），任务版本仍为初始值；记录实际投递延迟，最终pending/failed均零。不同采样时刻没有看见短暂pending不代表没有执行消息，实际outbox/inbox事实另行证明。

独立资金汇总使用POSTED事实，而不是浏览器页面总额：

```sql
SELECT kind, count(*), sum(amount)
FROM adc_cash_entry WHERE state = 'POSTED'
GROUP BY kind ORDER BY kind;

SELECT state, count(*) FROM adc_reconciliation_match GROUP BY state;

SELECT count(*), sum(total_amount)
FROM adc_visit_record_version WHERE state = 'PUBLISHED';
```

期望收款50100.10、退款100.10、设备支出及冲回各50.05元；患者净资金50000元。502张账单50200元与实收分开。有效匹配为29/525笔资金，剩余5001条外部流水没有被自动平衡。完整判定与来源摘要见 acceptance.json、database_checks.json和observation.json；私有账号、逐请求样本和患者标记留在本机受限目录，不上传。

本轮没有重做空库恢复、真实24小时、独立云主机或二十诊所测试。R1与R2.3历史证据保持原日期。失败输出保留，不缩小负载或删掉失败来代替完整复验。

思维导图：同一版本 → 同一代表性分母 → 单独附加活动 → 真并发与时间 → 原行摘要 → 金额/匹配/消息 → 明确范围。
