# RC1：两条可复现课程演示路线与核算清单

只使用合成资料。本文件为操作规约；2026-10-13的Mac执行结果见[G3浏览器验收](G3_BROWSER_ACCEPTANCE.md)。Windows安装/初始化与原数据导入按RC_WINDOWS_ACCEPTANCE.md；Mac按MACOS.md完成。记录实际时间、版本、角色、输入、可见结果及数据库后置事实，不将点击次数记为业务成功。

## 路线A：从新资料到季度核对（可分场演示）

|序号|角色|操作及输入|必须核对的事实|
|---|---|---|---|
|A01|技术|基础目录登记新牙医和两个资格类别；登记两条关联|稳定新工号、两项关联；没有自动账号/权限/出诊；资格记录不等于执业核验|
|A02|技术|建立普通演示账号并授予该牙医身份，核对关联|非技术普通账号；不能凭superuser绕过业务身份|
|A03|主管|本店创建未来可用出诊（例如次日09:00—12:00）|医生/诊所正确，无跨店时间冲突|
|A04|前台|新建合成患者；过敏信息保持真实演示输入UNKNOWN|稳定患者编号，不把未知改成无过敏|
|A05|前台或患者门户|选择时段并确认预约；只到预览时停一次|预览无预约；确认后唯一预约；重复确认不多建|
|A06|前台|在演示现场单独确认到诊|真实到诊状态与时间；患者不能自行伪造|
|A07|牙医|复核实际信息，确认演示治疗及数量|由负责牙医确认；记录治疗不等于完成结算|
|A08|牙医|完成就诊，保存结算|逻辑账单唯一，版本发布；金额等于已舍入行金额之和|
|A09|财务|调整当前标准价后再查看原账单|原行单价、地址/抬头快照不追溯改变|
|A10|牙医→另一财务账号|申请数量/单价误录更正并独立审核|保留旧版本，新版本成为当前；同账号不得自审|
|A11|财务|纳入有收入和只有成本的牙医，录入/确认费用，确认纳入清单|缺失不同于0；0也需确认；未纳入开单牙医阻止总体结论|
|A12|总部/财务|查询季度、导出核对，检查修订后收入|按完成时间归季度；每逻辑账单只计当前版本；不等于现金收款|

为了复现精确数值，可在专用测试库运行tests/test_release_chains.py；其中身份与目录由FixtureMixin建成，不声称该测试已经覆盖A01/A02每个真实界面。完整UI人工执行必须另填记录。

## 固定独立核算表

机器输入及手工预期位于tests/data/release_oracles.json，不能调用生产函数生成自己的预期值。

- 0.500 × 0.01 → 每行0.01；两行合计0.02，不是先乘积相加再舍入的0.01。
- 1.125 × 99.99 → 112.49；2 × 99.99 → 199.98。
- 牙医1收入199.98、用品10、运营20；牙医2无收入、用品50、运营50：总利润69.98，正利润10%基金测算7.00。
- 同一逻辑账单更正至99.99后：利润-30.01，基金暂不计算（本项目零/负利润政策，不是通用会计规则）。
- 纳入成员缺失成本或成本草稿为0时都不能发布总利润；明确确认0时才可参与计算。
- 成熟预约组：到诊6，患者取消2，诊所取消1，爽约1，待核实3，改期前身5；取消率分母9、患者取消率22.22%、爽约率11.11%、完整性76.92%。改期前身排除，未成熟记录由数据库selector先排除。
- 北京时间7月1日00:00对应UTC6月30日16:00；半开区间保证不同时属于第二、第三季度。

## 路线B：暂停新增到协调复核及出诊维护

|序号|角色|操作|必须核对的事实|
|---|---|---|---|
|B01|主管|选一条有预约的未来出诊，预览并确认暂停新增|保留既有预约/有效邀约，不释放牙医时间|
|B02|患者/前台|尝试新约或改入暂停出诊；另核对暂停前有效邀约|新创建被拒；旧有效邀约仍可按原期限接受|
|B03|主管|发起停用或调整目标的协调任务|一条有效任务，原预约未变更，存在Outbox待派发|
|B04|前台|查看通知；明确标记已读；再另行受理任务|已读不受理；受理后负责人明确|
|B05|前台|核对原预约/邀约，通过原流程单独处理；记录有限声明|声明不能证明患者同意，也不能清除预约阻断|
|B06|前台|仍有受保护业务时尝试提交复核；合法处理后再提交|前次拒绝，后次保存事实摘要；不为排班而取消接诊|
|B07|另一账号主管|独立复核；提交后发生变化时退回重核|同一账号切角色不能自审；旧摘要不能通过|
|B08|主管|任务通过后回原出诊，另行停用或替换|通过任务不自动维护；旧时间/编号保留；替代继承暂停|
|B09|主管|经另一次确认恢复新替代出诊接收（适用时）|不自动预约或补发邀约；旧草案/旧确认按修订拒绝|
|B10|主管/技术|停止worker，产生新任务事件，再重启worker|任务已保存、消息待发；恢复后去重，不重新执行任务|

## 操作完整性与负例

每条主链至少检查：只读、非当前角色、其他诊所ID、旧标签页、重复确认、回执未知、空数据、手机320/390px、大字模式、Tab键可达；多身份始终先选身份再选店。

版本到期、依赖安装、数据异常、锁竞争或页面错误均记录首个失败。不能使用“步骤都点过了”替代业务后置事实。

课程答辩展示顺序：业务问题与边界 → R4.4原图的主要场景 → RC新增协调/通知模型 → 任选两条主链片段 → 固定核算样例 → 一个拒绝场景 → 实际证据和未完成范围。


## B1.1：取消分析 → 联系跟进 → 措施复核

1. 主管在本店工作台进入[取消时段分析](/operations/cancellations/)，选择完整期间和星期、时段，核对每格原数量、分母及完整性。没有足够样本就先核实资料，不能根据偶然高比例下结论。
2. 前台在[取消原因跟进](/operations/cancellations/followups/)核对原取消说明，实际联系后登记原因、结果、责任和下次期限。患者接受另约时通过“办理另一次预约”正式确认，再回填成功编号；跟进本身不创建预约或发送外部消息。
3. 主管针对同店时段[建立措施](/operations/improvements/)，指定执行人、期限和可核对的完成标准。负责人从本人措施开始、记录实际办理并提交；另一主管核对后续完整窗口、样本和可比性，复核或退回。
4. 当前开始的措施等待真实后续窗口结束。验收中明确标注的历史合成措施只演示复核，不作为四周真实改善。原取消预约、治疗及资金历史保持不变。

见[完整业务合同](B11_APPOINTMENT_IMPROVEMENT.md)与[执行证据](evidence_b11/README.md)。这是一条新的业务演示路线，不改变历史RC验收结果。
