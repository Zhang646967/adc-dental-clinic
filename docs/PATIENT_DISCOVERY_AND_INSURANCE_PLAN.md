# 患者门店发现与中国医保开发计划

公开找店 → 按需登录 → 明确就诊人 → 统一预约 → 地区医保规则 → 收费及资金核对。

**分批实施中，2026年10月24日。C0.4已形成源码候选；C1-WX和C6.1尚待实施，C6.2等待真实机构条件。** 本计划承接[中国业务调研](research/CHINA_PATIENT_ACCESS_STUDY_20261024.md)，细化[商业总计划](COMMERCIAL_V2_MASTER_PLAN.md)的 C0、C1 与 C6。C1.1至C2.3的既有交付和 C3至C8的剩余要求按原范围保留。C0.4采用三份追加迁移，独立验证库结构已只读核对；当前安装及外部验收分别记录。实际ER见[已观察结构](database/README.md)。

## 已确定的产品规则

1. 小程序仅面向患者与有权代约的人，先进入公开首页。员工使用独立网站入口和现有工作上下文，不在患者小程序中选员工角色。
2. 定位由用户主动选择，默认按**由近到远**排序；手动城市或区域选择始终可用。首批八省会二十店采用明确标识的合成配置。
3. 对外名称、地址入口、电话及营业信息经维护后发布；展示营业状态与资源可约状态分开。前台继续维护日周排班，主管维护门店及资源资料。
4. 微信账号、核验手机号、患者身份、预约代办及临床同意分别管理。普通微信登录不取得居民身份证信息。
5. 医保先覆盖湖南目录与合成流程，随后按具体定点机构办理真实接入；不得使用全国统一硬编码报销比例。

## 第一批 C0.4 门店发现与访客入口

**交付主线：** 首次打开 → 主动定位或选择城市 → 查看门店与服务 → 查看公开可约日期 → 按需登录 → 选择合法就诊人 → 原候选与确认流程。

- 扩展网站 `/clinics/`、公开首页及原生小程序公开门店页面；复用已发布服务目录。仅增加必要的匿名只读投影，不开放现有员工或患者业务接口。
- 两个网站登录通道在服务端限定可激活岗位：患者入口只激活有效PATIENT，员工入口仅选择已授权的非患者岗位。多角色账号按进入的通道激活；缺少该通道身份时给出对应办理入口，不能自动切到另一个岗位。认证、会话和原工作上下文机制继续共用。
- 将门店业务身份与公开资料分开。公开资料包含展示名、行政区、地址入口、坐标及来源、公开电话、周营业时间、营业例外和资料版本。
- 维护营业信息时核对科室开放与资源安排。停诊影响已有承诺时进入前台协调；更新公开文字不能静默取消预约或释放有效邀约。
- 限制公开字段为经过发布的门店、服务及必要执业展示信息；不包含排班人员私有联系方式、内部备注、患者、余量成因或预约明细。
- 定位坐标在客户端用于排序；需要地图服务时按该能力申请权限和配置，精确位置不进入常规请求日志。用一致坐标系计算直线距离；未定位不显示精确距离。
- 登录延续绑定选定门店与明确服务，随后重新查询候选并确认就诊人；过期或已下架内容返回可以继续选择的页面。查到候选不占用资源。
- 业务主键、编码和历史单据保留。公开别名与原名称通过正常维护动作衔接，不能直接批量 SQL 改写旧名称和历史快照。
- 先完成长沙四店的完整服务和资源配置。其他省会门店按配置准备程度发布，不因导入目录就生成排班、治疗或资金。

完成门槛：网站与小程序的访客找店、按需登录和正式预约路线贯通；拒绝定位、营业例外、服务撤回及跨店授权测试通过。二十店目录的展示验证与二十店业务容量验证分别记录。

思维导图：公开资料 → 发布投影 → 位置及营业 → 服务选择 → 登录延续 → 就诊人 → 原预约确认。

## 第二批 C1-WX 微信账号与渐进身份

**交付主线：** 微信登录凭证 → 服务端校验 → ADC 患者渠道账号 → 主动绑定手机 → 本人建档或既有档案核验 → 原患者切换。

- 外部账号绑定以平台、AppID 和 OpenID 为稳定身份范围；UnionID 仅在真实返回且符合账户绑定规则时使用。服务端保管密钥并验证凭证，客户端不传入一个 OpenID 就取得登录权限。
- 已有 ADC 账号通过其现有认证或明确的恢复核验办理绑定；已绑定、换绑及解除留存事件。重放外部凭证、同名、同手机号不成为另一个账号或患者的登录依据。
- 首次微信认证只建立患者渠道身份，不产生员工角色、PatientAccess 或代约授权。新患者可提交建档申请，前台按明确流程完成必要资料和本人绑定；旧患者有专门核验入口，查询结果不公开透露匹配档案。
- 将账号联络、就诊资料与接诊必需信息逐项分清。当前完整患者档案的地址及紧急联系人等字段在正式建档时处理，不用微信登录自动填充假资料。
- 手机授权成功记录核验来源及时间；手机号变更不重绑患者。无该接口资格时保留已分配账号及人工核验路线；短信替代需要实际短信服务后另行验收。
- 身份证及医保身份按必要场景核验。默认不接入人脸核身；若具体机构确有需要，再按产品准入和最小数据要求接入。
- 已验证代约人继续按 C1.1 的患者、诊所、动作、期限和授权版本办理。撤权、切换患者及旧预览沿用原锁与回执规则。

本地接口替身仅用于开发。真实微信登录及手机号验收需要注册主体、AppID、实际开通的接口、服务端私有配置、HTTPS 请求域名及开发工具和真机；不在聊天或公共仓库存放 AppSecret。

思维导图：外部凭证 → 账号绑定 → 核验联络 → 本人或授权就诊人 → 原预约权限；实名核验按办理事项增加。

## 第三批 C6.1 医保准备与合成结算

**交付主线：** 湖南目录版本 → 机构协议配置 → 就诊身份及已执行费用 → 合成预结算 → 明确确认 → 分担结果 → 退费与基金到账核销。

1. 先取得并核对湖南2026年口腔支付附件及长沙适用目录。保存原始政策来源、地区、有效期、项目代码、计价单位、支付限制和映射版本；政策未知与明确不覆盖分别显示。
2. 机构代码与定点协议属于具体诊所。医师核对临床项目含义，财务维护目录候选并由另一财务复核，主管确认本店协议范围，总部仅查看汇总；财务独立审核结算及核销。新增维护动作在本批权限合同中明确，技术管理员不代替业务审批。
3. 实际收费项目仍来自原执行与账单流程。医保目录映射不能增加治疗、改变旧账单价格或以新的项目拆分原费用。目录变更不回写已结算记录。
4. 保存参保地、就诊地、参保类型、待遇核验及外部凭证引用；用户所在城市不替代参保地。患者自行填写“已参保”不能成为待遇核验结果。
5. 预结算只是待确认的分担结果，正式结算保留业务请求编号、就诊人、费用版本、返回凭据和分担明细。处理中或结果未知时查询原请求，不直接重发新结算。
6. 将患者自付、个人账户支付、统筹基金应收与到账分开。合成示例1000=300+700必须在患者余额、应收、现金和收入中独立核对，不能将基金到账重复记收入。
7. 原结算撤销或更正、患者退费及基金应收冲销保留明确顺序和关联；不在医保状态未知时声称退费全部完成。
8. 基金批量拨付按申报明细分配，扣减、争议及未到账保留单独处理依据。不得将所有扣减自动挂成医保欠费或患者欠款，不自动生成补差收款。

初期采用合成目录及模拟外部结果，页面和输出标识模拟环境。真实药品和耗材的医保计费继续依赖 C4、C5 的实际执行及相应权限，不能绕过药事审核。C3 签署、必要同意与归档仍为正式替代门槛。

思维导图：政策及协议 → 真实费用来源 → 预结算与确认 → 分担结果 → {患者清偿、基金应收} → 撤销或到账核销。

## 第四批 C6.2 具体机构真实接入

在机构提供实际医保协议、医疗机构编码、当地接口规范、测试凭证、所需接入网络和经办对接人后，完成对应适配。原生微信手机号或医保电子凭证的开通结果不能替代医保结算接口准入。

验收包括参保身份、目录映射、费用上传、预结算、正式结算、超时查询、重复确认、撤销、部分或全额退费、基金清算及独立对账。实际字段和业务顺序以选定地区接口合同为准，不预设一个全国通用公开 REST API。后续省份分别加入版本与适配，不复用湖南比例。

课程云演示沿用合成数据安排。真实境内医疗数据的部署地点、数据处理及医保网络要求在商业部署合同中另行确认，旧香港课程服务器方案不是其准入证明。

## 模块与关系设计

以下为逻辑设计，实体名与物理表由对应批次 ADR 最终确定。

| 数据及关系 | 所属模块 | 核心规则 |
|---|---|---|
| Clinic → 公开资料及发布版本 | 门店目录 | 同一业务门店保留身份；展示名、地址坐标和发布历史可追溯 |
| 公开资料 → 营业区间及例外 | 门店目录与排班边界 | 关联原开放时间与可约核验；公开改动不撤销原承诺 |
| Account → 外部身份绑定及事件 | 账户认证 | 平台与应用内身份唯一；绑定不授予患者或员工权限 |
| Account → 手机核验 | 账户认证 | 来源、有效性及变更事件留存；不是患者合并键 |
| Patient → 身份核验依据 | 患者身份 | 自述、核验和必要凭证分开；敏感信息不进入公开目录或日志 |
| PatientAccess / AppointmentGrant → 预约回执 | 原患者及排班模块 | 保留原本人及代约边界、共享资源锁和唯一业务结果 |
| Clinic → 定点协议 → 地区目录版本 | 医保模块 | 机构、地区、有效期及项目范围明确，协议状态不能复制给另一家门店 |
| 原实际费用 → 医保申报行 → 结算版本 | 医保模块 | 费用来源唯一且可追溯，外部状态变更不改写临床和原始收费事实 |
| 结算 → 分担明细 → 基金应收 → 清算分配 | 医保与财务边界 | 承担金额、实际到账、核销和扣减独立；一个批次可对应多笔申报 |

每个实施批次保留当前49份迁移，使用追加迁移。在独立迁移后的 PostgreSQL 中生成实际表、字段、外键和 ER，核对旧历史后再更新课程报告的已实现设计。规划关系不绘入当前物理 ER。

各批次执行相关完整回归、真实 PostgreSQL 约束和并发、390px大字号和键盘、双端真实后端业务验证，以及含新增事实的独立加密恢复。微信平台、实际地图或电话服务、真实医保及容量证据按已执行环境分别记录。首次二十店业务启用前另做代表性业务容量验证，不从目录数量推断容量。

实现通过后按原交付流程取得准确提交 CI、保护原数据和配置、更新本机，并更新固定文件名的 Word、PDF 及实际 ER。本次规划文档的核对不算上述功能通过验收。

思维导图：业务问题 → 岗位 → 公开或授权操作 → 模块所有权 → 数据与状态 → 失败回应 → 可执行场景 → 分批交付。
