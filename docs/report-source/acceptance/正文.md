# 第一章　系统范围与验收入口

## 1.1　沿着一笔就诊验收
患者原计划周一上午到店，因日程变化希望改到次日。患者先核对原来约的是哪家店、哪位医师以及起止时间。只有确认新的接诊安排后，才按新的时间到店。到店时，前台须在本店有权查阅的患者档案中找到正确的人。医师随后根据同一笔就诊打开检查记录，区分正在补写的草稿与已确认的内容。这三个决定贯穿本报告。
验收对象覆盖患者网页、患者微信小程序以及员工工作台。患者在两种渠道中核对同一预约。患者编号标识同一个人，就诊编号标识一次安排，病历版本标识一次确认的内容。三个编号的用途不同，交接时应说明所指的是哪一项。
### 表 1-1　岗位入口与首项核对
| 岗位 | 进入方式 | 首项可观察结果 |
| 患者 | 进入门诊首页，打开患者登录。手机使用获准的微信入口 | 确认当前就诊人，从就诊清单打开一笔预约 |
| 前台 | 从员工登录进入前台岗位，选择负责的门店 | 能在当前门店查询档案，按完整患者编号打开 |
| 医师 | 从员工登录进入医师岗位，进入检查记录工作台 | 能找到授权范围内本人负责的就诊及其记录 |
### 1.2　阅读顺序
仓库首页提供“进入门诊系统”和岗位指南，验收者可从该页取得当前有效的使用入口。
[打开系统与岗位指南](https://github.com/Zhang646967/adc-dental-clinic)
首页的门店与服务目录可直接浏览。岗位账号按机构授权取得。切换角色后，应重新核对页面显示的门店、患者和业务范围。第 2 章说明各岗位交接什么，第 3 章给出办理规约，第 4 章解释数据如何留存，第 5 章提供可逐项复核的结果。附录按原编号保留各项用例。

# 第二章　门诊业务与岗位职责

## 2.1　确定研究对象
以连锁口腔门诊为研究对象，患者向门诊提出预约、诊疗和费用核对要求，是门诊外部的业务执行者。前台人员和接诊医师在门诊内部承担业务责任。以软件为研究对象时，患者、前台人员和医师都能直接操作相应入口，分别是系统执行者。图 2-1 仅从患者角度概括组织对外提供的结果。

就诊安排在患者确认后形成。到诊登记说明患者已到门店，实际接诊由负责医师办理。完成治疗、形成结算单和收到款项各有独立凭据。一条记录未包含的事实，后续岗位应继续核实。

患者出示预约信息后，前台先核对就诊人，再登记实际到诊。医师取得本人负责的就诊，询问主诉、核对病史，记录实际检查所见。医师确认后，才出现相应的确认版本。图 2-2 选取正常办理顺序，交接中涉及的预约资源与收费规则分别在后文展开。

### 2.3　其他岗位的责任
诊所主管负责本店服务目录和相关协同复核，总部查看授权范围内的跨店经营情况。财务人员办理收退款审核及对账。药房与护理流程在获准的隔离验收环境中按本店有效职责开放。系统管理员维护技术账号和授权。岗位名称、当前工作区、门店和专业操作范围共同限定一次办理。
预约代办与医疗代理分别核验。取得代约资格的人可以在授权内协助预约。调阅报告、账单、病历副本另有各自的权限和范围。门诊以当前有效授权核对每次操作。

## 2.4　治疗、药事和财务的岗位交接
医师确认的方案描述将要办理的事项。医师按实际实施情况登记处置，接续岗位按发生的事实办理发退、收费与复诊。将建议、执行、记账和收款分别留存，能在患者询问费用时找到对应责任人与依据。
### 表 2-2　各岗位的处理对象
| 岗位 | 负责办理 | 交给下一岗位的凭据 |
| 负责医师 | 检查、确认文书、告知、登记实际处置、明确后续安排 | 准确版本、实际执行情况、后续要求及建议窗口 |
| 门店药师、护理人员 | 在各自有效职责范围内办理处方调配、发退药或护理执行 | 相应的审核决定、实际发退或执行记录与批次 |
| 门诊前台 | 查验患者身份、记录到诊、联系复诊、按凭据办理结算相关事项 | 预约编号、联系结果、已发布结算单、资金办理凭据 |
| 财务人员 | 独立核对收退款凭据、渠道流水、日结与差额 | 实际记账金额及审核轨迹、逐笔对账结果 |
| 门店主管、总部 | 复核本店服务与协同事项，按相应范围汇总经营资料 | 服务发布版本、门店实际经营结果与核对记录 |
| 系统管理员 | 维护普通账号、岗位及允许范围 | 相关授权、启用状态与操作留痕 |
处方、调配、库存与护理的本版入口限已启用相应功能的隔离验收环境。开方要求本人负责、已到诊、已有确认病历及本店有效开方职责。审方由另一账号持本店有效审方职责办理。调配与审方分别授权，发药人与开方人分离。护理执行与无菌放行各需本店单独、有期限的职责。真实处方、用药目录、签署及专业岗位资格须由机构另行审定。
就诊人与操作人应分别核对。患者本人以自己的身份阅读报告。代约人员仅在预约授权有效期及适用门店内办理预约。医疗代理另按具体材料与用途办理。工作人员切换门店或岗位后，需要按新工作范围重新取得记录。

## 3.2　患者确认改期
### 表 3-2　患者自助改期用例规约（SU-40）
| 项目 | 内容 |
| 执行者与触发 | 已获授权的患者从现有预约选择调整时间。代办人仅能办理其有效授权覆盖的事项。 |

## 3.3　前台核对同名患者
### 表 3-3　患者档案查阅与到诊衔接规约（SU-03、SU-06）
| 项目 | 内容 |
| 执行者与触发 | 患者到店，请前台核对预约。前台在当前门店进入患者档案。 |
| 输入及前置条件 | 当前岗位具有本店授权。取得姓名或完整患者编号，待办预约属于该就诊人。 |
| 基本路径 | ① 按姓名查找。② 遇到同名标识时，逐位核对患者提供的业务编号。③ 打开对应档案，核对该次预约的门店与时间。④ 返回清单时回到先前结果。⑤ 具备到诊条件后再办理登记。 |

## 3.4　医师维护与查阅记录
### 表 3-4　检查草稿与确认版本规约（SU-69、SU-70、SU-71）
| 项目 | 内容 |
| 执行者与触发 | 负责医师开始检查、续写记录或核对既有确认内容。 |
| 前置条件 | 已选有效医师身份。该患者与本次就诊在其有效查阅或操作范围内。初次记录须符合实际到诊条件。 |
| 基本路径 | ① 在检查记录工作台定位本人负责的就诊。② 核对患者编号和时间。③ 按目的打开草稿或当前确认版。④ 需要确认时核对内容并明确提交。⑤ 需要追溯时按版本号打开历史内容。 |
| 更正与冲突 | 有更正草稿时，原确认版继续可读。并发更新或版本变化时，重新取得当前事实并比较后再提交。 |

### 初诊与复诊文书
结构化检查与完整病历文书各自维护版本。医师从检查记录工作台可进入文书与待办，核对是初诊还是复诊，按准确版本阅读、确认或更正。草稿允许继续编辑。打开当前或历史确认版供查阅时，不能以草稿内容覆盖原确认内容。

## 4.1　领域对象及其关系
患者标识持续使用，预约标识对应一次计划安排。一次预约至多形成一个本次接诊，在实际到诊并开始记录前可以没有接诊。一次接诊可有多份依次留存的检查记录版本。图 4-1 表达业务概念和多重性，具体数据表见图 4-4。
@model 4 | 图 4-1　患者、门诊、预约与检查记录的分析类图
### 表 4-1　标识与时间的用途
| 识别对象 | 验收时观察的字段 | 判断依据 |
| 就诊人 | 完整患者编号、当前身份 | 同名患者仍各有其独立档案 |
| 预约 | 就诊编号、门店、医师、计划起止时间 | 改期后，原编号保留原时间，后继有自己的编号与时间 |
| 临床记录 | 接诊所属就诊、版本号、确认内容 | 本次可同时存在已确认内容和待确认的更正草稿 |
| 费用 | 结算单编号、发布版、收款及退款 | 修改账单发布版本与登记实际资金是两项不同业务 |
### 入口与责任
网页与患者小程序共享已获授权的预约资源和办理规则。岗位信息和当前门店由服务端核对。直接打开已知编号也须再次核实身份。页面提供可用操作，数据权限仍按当前就诊人与业务范围判定。

## 4.3　预约状态和业务事件
@model 6 | 图 4-3　单条就诊记录的状态机
图 4-3 的主体是单条就诊记录。改期表示原记录进入“已改期替代”，同时另外生成一条“已预约”的后继。原记录不会沿状态线再次变为“已预约”。已到诊表示前台完成登记。医师接诊、记录与完成实际治疗另有业务事实。
### 表 4-2　对状态容易产生的三种误读
| 页面上看到的事实 | 可以得出的结论 | 还需另查的事实 |
| 已收到候补邀约 | 在有效期内可以核对并选择是否接受 | 是否明确接受并生成正式预约 |
| 已到诊 | 已登记到店 | 医师是否实际检查、实施治疗或关闭本次就诊 |
| 已发布结算单 | 可核对当前应计费用 | 已收、已退、尚需支付或应退余额 |
### 责任留存
同一人切换角色仍是同一实际操作人，不能据此完成要求独立人员复核的环节。撤回报告、更新账单或追加病历更正时，分别保存其业务事件和历史版本，允许按原始凭据追溯。

## 4.4　物理数据与关系核实
@model 7 | 图 4-4　患者预约与临床版本的物理关系摘录
图中列名取自实际 PostgreSQL 数据库。PK 表示主键，FK 表示外键，UQ 表示唯一约束。每份预约办理回执对应一个就诊编号。一个接诊可以先没有草稿和确认版本。草稿关联接诊并可记录更正所依据的版本，确认版按本次接诊和版次保持唯一。
### 表 4-3　数据库中可复核的关联
| 外键或约束 | 业务含义 |
| 就诊记录的 patient_id | 每笔就诊必须归属一名患者，同一患者可有多笔就诊 |
| 就诊记录的 replaces_visit_id | 后继指向原预约。普通预约该字段可以为空。同一原约至多有一个直接后继 |
| 回执的 visit_id | 同一次预约结果不会对应多份相同业务回执 |
| 确认版的 previous_id | 更正版本可追溯上版。第一版没有上版 |
| 确认版的 encounter_id、revision | 同一接诊内的版次唯一，不同接诊分开计数 |

## 4.5　应用结构与运行数据
患者从浏览器或微信发起请求。员工工作台通过网页进入。两种入口共用身份、排班、预约、资金和诊疗规则，向各岗位呈现其可读字段。服务端负责验证当前身份、限制门店和记录范围，并在确认时检查业务状态。持久业务数据由 PostgreSQL 保存。
### 表 4-4　应用层次与职责
| 层次 | 代表组成 | 验收者可验证的行为 |
| 交互入口 | 公开服务目录、患者服务中心、前台与医师工作台、微信患者端 | 各岗位有独立入口，同一条授权记录的业务编号与状态可以对照 |
| 身份与工作区 | 账号、工作身份、有效岗位、当前门店、当前就诊人 | 切换身份后旧页面不能继续代替新身份提交 |
| 业务办理 | 预约与候补、临床检查与文书、处方、结算、复诊和出诊协调 | 最终确认与查询分开。预览不占正式结果，实际执行后有相应凭据 |
| 持久数据 | PostgreSQL 的主外键、唯一约束、受保护历史及审计记录 | 相同请求回查原结果。已确认版本与历史资金条目均可溯源 |
| 对外渠道 | 微信身份服务、短信通道以及需门店开通的外部服务 | 可用范围以对应机构的授权、配置及独立受理结果为准 |
数据库的完整关系目录另按患者身份、门店资料、出诊与预约、检查与文书、资金、药事、耗材和护理等主题编排。第五章三条主要路线只提取与办理决定有关的字段。机构配置、人员账号、私有凭据和患者个人资料不随报告分发。
