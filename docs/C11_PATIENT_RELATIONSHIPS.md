# C1.1 患者关系与预约代办

前台受理 → 明确职责核验 → 有效期授权 → 选择就诊人 → 共用预约、改期和候补 → 原约及决定历史保留。

本阶段实现网站和原生患者渠道的预约代办。关系受理、核验依据、授权和操作账号分别保留；本人绑定沿用原 PatientAccess。[数据与权限合同](C11_IDENTITY_CONTRACT.md)、[执行证据](evidence_c11/README.md)、[实际数据库 ER](database/README.md)分别记录规则、执行结果和物理结构。

## 办理方法

1. 技术管理在账号治理中明确分配当前店前台的“患者关系核验职责”，须重输密码并核对目标账号。普通前台岗位不会自动获得核验权限。
2. 前台进入 `/patients/relationships/`，按本店已有患者档案受理关系，记录关系类型和说明。可暂不填账号；账号由原有账号治理创建，之后人工核对具体账号再关联。
3. 具有核验职责的前台核对患者、关联人、账号归属及依据，填写内部依据编号、说明和截止时间，预览后明确确认。父母、监护人和患者委托人可获本店预约代办；联系人、普通亲属仅保留关系。
4. 患者或代约人登录网站，进入“切换就诊人”；小程序有相同的患者选择页。无本人绑定的代约账号须先选患者。每页显示当前就诊人及本人／代约身份。
5. 新约、普通改期、有效邀约替换、候补登记、邀约接受／拒绝、退出与取消共用既有预约和资源命令。选择患者不会占位；最终确认重新核验授权及冲突。
6. 前台可暂停、撤销或拒绝关系。暂停后恢复需要重新核验，决定追加保存；撤销和到期不取消原预约或候补，继续从既有前台入口明确协调。

预约权限不包括诊疗记录、账单、支付和临床知情同意。系统不凭手机号、姓名或微信来源自动合并患者或授予访问权。核验记录是工作人员对依据的可追溯登记，不构成软件对法定身份或专业资质的认证。

## 一致性与历史

网站与小程序共用服务端当前患者和授权版本。切换患者后旧预览失效；原生客户端还会清除待确认内容并丢弃旧请求的迟到响应。失效授权不能重放旧成功结果来读取患者数据，合法重试则返回已保存的当前结果。

普通患者预约及改期回执保存本人绑定或代约授权，恰有一个来源。邀约新增沿用 WaitOffer 的唯一接受结果和实际操作人审计，不补造旧回执。不同合法操作者为同一患者预约时共用原患者、医师及物理资源锁。

新增三个业务表和三份追加迁移；原 40 份迁移保留字节。关系决定事件由 PostgreSQL 阻止更新和删除。当前实际结构为 73 表、181 条 SQL 外键、43 项业务触发器；报告与七幅 ER 均来源于数据库元数据。

## 验证与交付

完整本地回归通过 1,095 项规则、1,502 项 PostgreSQL／HTTP／并发测试，其中 28 项为关系授权场景。五诊所真实 Chrome 与原生 Page 逻辑通过 HTTP 共用后端，覆盖选患者、预约、改期、候补与撤权；另核对七岗位、核验职责分配、390px 大字和键盘操作。12 页官方离线语法编译通过。

准确应用提交 CI、加密独立恢复、原实例复制升级与保护更新按执行顺序追加到证据目录。微信开发者工具实际预览、真机、体验版及独立云端仍待条件具备后验证；旧容量与持续观察证据保留原范围，不据此宣称当前商业临床上线。

思维导图：患者关系 → {受理、账号核对、核验职责、依据、有效期} → 本店预约授权 → {网站、小程序、就诊人切换} → {预约、改期、候补、取消} → {资源互斥、历史保留、撤权协调}。
